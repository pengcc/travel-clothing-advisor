# Approved execution contract — Travel

Select only when a current reviewed Plan or equivalent target-owned execution contract **and explicit implementation authorization** govern the requested pass. Reuse them; do not re-plan just to change formats.

For an Issue-backed formal Plan follow docs/collaboration.md:
1. Resolve the Issue body's single **current** Implementation Plan vN comment permalink and content.
2. Resolve the distinct clean Formal Plan Review referencing that same exact Plan version and current evidence.
3. Verify the separate explicit **user Approval** record and its actual source/context; never infer Approval from an assistant comment, Issue/PR creation, review verdict or Plan status.
4. Compare the current target and accepted Task Decisions against the reviewed Plan for material drift, scope, acceptance, risk, rollback, validation and STOP conditions.

An incomplete/stale/ambiguous Plan, changed governing authority, missing review/approval or unsupported validation requires STOP to the current Plan/authority owner. Material correction follows docs/collaboration.md: new version, independent review and renewed Approval before affected execution. Do not silently update approved Plans from an implementation branch.

Implement only the currently authorized work, including authorized documentation or Skills changes. For initial implementation, use a dedicated delivery branch and create **one change PR** linked to the Issue. For authorized remediation of an existing PR, resolve its current base/head and continue on the **same delivery branch and PR**, without creating a replacement branch or new PR. Use actual target validation and retain independent Implementation Review/re-review; Plan Approval and merge authority remain governed by docs/collaboration.md. No donor Task State, stored activation checkpoint, Task Workspace or automatic merge.
