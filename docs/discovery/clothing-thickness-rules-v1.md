# Travel Clothing Advisor — 六级穿衣厚度与天气推荐规则 v1（候选）

> 2026-10-14。状态：**待评审产品规则候选**，非已证实人体保暖阈值、非真实出行保证、非应用实现。仅把最近明确的产品方向具体化：**按目的地与旅行日期推荐衣服是否偏厚/偏薄、早晚是否要加层，以及风雨提醒**。仍处于 Product Discovery；是否采用或进入开发另行决定。

## 用户需要什么

默认输入：**德国城市 + 出行日期/日期范围**。可选：**普通／怕冷／怕热**；正常城市观光是默认活动，不要求创建衣橱、输入衣服品牌/重量、登记行李空间或填写复杂问卷。

最小输出：①建议的**主要厚度及衣物例子**；②是否建议携带**可增减的一层**（早晚或温差）；③是否建议**挡风、防雨、雨雪鞋帽等**。每条建议注明所用日期范围和天气资料时间。回答是天气条件下的一般性推荐，不保证个体舒适度。

## 1. 六级“穿着组合厚度”（不是六类必须带的衣服）

| 等级 | 意义 | 人能理解的组合例子 |
| --- | --- | --- |
| L1 清凉 | 炎热天气，尽量透气 | 短袖/轻薄衣裤 |
| L2 轻薄 | 温暖天气 | 短袖或薄长袖，必要时备用很薄的外层 |
| L3 轻外层 | 舒适至稍凉 | 薄长袖，或薄上衣搭配可脱的轻外套；外套不要求整天穿 |
| L4 中等保暖 | 偏凉 | 长袖为基础，按时段加抓绒、毛衣或适中外套 |
| L5 加强保暖 | 较冷 | 保暖中间层 + 防风外套，或轻型保暖夹克/轻羽绒；**不必两套全带** |
| L6 冬季保暖 | 寒冷 | 保暖内搭 + 中间层 + 较厚外套；遇严寒或长时间户外可考虑厚羽绒、帽子手套 |

这是**整个推荐穿着组合**的等级，不能相加成“L3 外套 + L5 羽绒 = L8”。表中例子是**替代搭配或可选层**，不是强制穿齐的清单；例如 22°C 的普通城市步行者不必因为标为 L3 就穿上外套。雨衣通常是额外的外壳能力，不自动提高保暖等级；同一种外套名称的保暖能力也并不固定。

## 2. 初版天气到厚度映射（产品试算值，而非科学阈值）

对于默认普通体感、城市步行，按**旅行期间典型白天气温**先选择一个主等级：

| 白天气温 °C | 主等级 | 常见表达 |
| --- | --- | --- |
| >= 28 | L1 | 短袖、轻薄衣服为主 |
| 23 至 <28 | L2 | 短袖/薄长袖为主 |
| 18 至 <23 | L3 | 薄上衣或长袖，偏凉时再穿/带薄外套 |
| 13 至 <18 | L4 | 长袖为主，按时段增加抓绒或适中外套 |
| 6 至 <13 | L5 | 可用抓绒＋外套等分层组合；较怕冷时考虑轻羽绒 |
| <6 | L6 | 冬季穿着组合，具体厚度随活动调整 |

**白天气温定义：** 正式建议优先使用出行时间对应的逐小时/白天温度，而不是机械使用全天最高温。下方历史检查只有 DWD 的日最高/最低温；**日最高只作为白天较暖条件的粗略代理**，不是对全天推荐的充分验证。

**最简单的修正规则：**

- **早晚温差：** 比较白天与可信的早晚外出时段。如果夜间/清晨明显冷于白天、对应更高的保暖等级，建议**随身带一件可穿脱的中间层/外套**。仅有日最低温时只能说“早晚可能更冷”；最低温可能发生在凌晨，不能推断特定晚上一定如此。作为粗略标记，日最高最低差 >= 8°C 时提醒留意分层，但不是固定要求加厚羽绒。
- **风：** 预报持续风速约 >= 25 km/h 或阵风约 >= 45 km/h 时，额外提醒**外层挡风**；这些只是待调整的候选触发值。**不直接跳高一个保暖档**，也不使用未验证的体感公式。
- **降水：** 预报有明显雨/雪影响户外行程时提醒**可靠的防雨层、雨具或合适鞋**，不按“软壳”名称假定防水。降水概率/时段比孤立的全天雨量总和更适合用户建议；首版不声称统一的降水概率阈值已经验证。
- **体感：** “怕冷／普通／怕热”只影响**保暖层的可选程度与文字表达**，不对全部气温机械执行 L±1。怕冷时在偏凉条件下优先多备一件可脱层，怕热时优先少穿中间层；炎热天气不因怕冷就强加外套，严寒天气也不因怕热就取消基本冬季防护。风雨提醒**不随偏好取消**。接近温度档边界时允许给出相邻厚度选项，例如 12.9°C 和 13.1°C 应有相近建议，不应仅因跨界就从“轻羽绒”突然变成“薄上衣”。
- **旅行多日：** 用行程中的**主要白天条件**给主推荐，再用明显偏冷/偏热或雨天补一句备用建议；不能把单个极端日变成“每天都穿厚羽绒”，也不能平均掉一段确实需要保暖的日子。若旅行跨多个温度档或跨越预报与历史期，分别说明较暖与较冷的条件，以及对应可增减的层，不自动要求各档衣物都带齐。

## 3. 日期与历史数据：同一衣物模型，两种资料来源

| 出行距离今天 | 产品建议类型 | 数据依据 |
| --- | --- | --- |
| 第 1–7 天 | 相对具体的每日/全程穿衣建议 | 可用的最新天气预报（关注白天、外出时段、风雨） |
| 第 8–14 天 | 初步携带建议 | 中期预报与变化范围；避免假装精确 |
| 第 15–30 天 | 季节准备建议 | 历史**多年**同期温度分布与降水特征，必要时用周尺度趋势补充；**不是逐日预报** |

上表天数按**每一个旅行日距离查询日的时长**计算，不是只按出发日划分；同一段旅行可能同时包含预报段和气候参考段，不能用单一数据精度覆盖整个行程。去年和前年可作最近年份的对照，但**不只使用两年**推断下个月。数据方案尚未选定：DWD Climate Data Center 有德国日观测史料，历史天气分析也可评估 Open-Meteo 的 reanalysis API；接入前需核对空间代表性、观测与再分析差异、数据缺失、许可和更新方式。

**每日重新计算**未来窗口的建议，但数据变化未改变衣服厚度时，文字不必每天重写。输出注明“天气数据更新时间”及“适用旅行日期”；不隐含项目已经实现定时任务。

**桌面结论：** 这 8 个真实天气切片可以覆盖夏季热天、夏季凉雨天、春季大温差、秋季变冷和冬季严寒。规则能产生明显不同而且*表面合理*的衣物厚度建议；**没有验证人体舒适度、实际用户选择、逐小时穿着、整个旅行或预报准确性**。不能据此称规则已“校准”。

## 5. 通过标准与范围边界

本次只需要判断一个问题：同一套短小规则能否在不同季节**大致避免过厚或过薄的明显推荐错误**，并用普通人看得懂的衣服名称输出。

正式实现前还要做最小检查：同城同天气、怕冷/普通/怕热变化是否温和；全天最低温与实际外出时间不一致时是否避免过厚建议；只下小雨时是否避免推荐整套冬装；跨季节旅行是否能同时提醒热天和冷天。正常的个体体感差异**不等于产品错误**。

**不在此轮做：** 个人衣橱、衣物重量/尺寸、复杂行李减法、安全省略证明、体感舒适度保证、AI 训练、自动发布程序、技术架构决定、真实用户参与者测试。本文件不更新既有 Blueprint/Baseline 的接受状态；若采用这一更简单的产品方向，后续应统一更新项目主产品定义，避免同时维护两套冲突的目标。


## 6. 可重复的真实历史天气规则回放（2026-10-14）

此节记录**实测历史天气 → 六级规则 → 自动产生文字建议**的一次可执行试验，**不是未来预报或可上线的 API 接入**。源数据来自 [Blick aufs Wetter：Berlin-Tempelhof 站 00433 的 DWD 日值公开表](https://www.blick-aufs-wetter.com/messwerte/historie/ort/Berlin-Tempelhof/00433?jahr=2025)，经过人工转录成 \`experiments/clothing-rules/berlin_tempelhof_2025_sample.csv\` 的 **26 个选定日期**；没有直接下载或比对原始 DWD ZIP。记录的是每日日最高、最低、降水、积雪深度、最大阵风；它们不能替代时段预报，历史天气不能拿来声称对未来旅行准确。

随本 PR 附上**无第三方依赖、仅供验证**的 Python 脚本和测试，方便在本分支直接重跑：

\`\`\`bash
python3 -m unittest discover -s experiments/clothing-rules -p "test_*.py" -v
python3 experiments/clothing-rules/validate_clothing_rules.py \
  --start 2025-04-15 --end 2025-04-19
\`\`\`

候选规则的初次自动输出总结：

| 真实历史日期 | 日最高温范围 | 规则主要推荐 | 特别应该提醒 |
| --- | --- | --- | --- |
| 2025-02-16～20 | 0～4°C | L6 冬季保暖 | 低于零下的日最低、实际积雪；保暖及合适鞋 |
| 2025-04-15～19 | 10.3～26.7°C | L3 薄长袖/可脱外套 | 两天明显变冷，最低日最高 10.3°C 对应 L5；带可增加的保暖层，另有雨、阵风 |
| 2025-07-01～07 | 24.7～37.6°C | L1 透气短袖 | 日最高降到 25°C 左右**仍不需要厚外套**；日夜温差可用薄层，部分日子有风雨 |
| 2025-10-14～22 | 11.1～17.4°C | L4 长袖＋按需加层 | 两天偏冷可增加保暖层；存在零下的**日最低温**，但不能当成全天温度 |

**回放发现并修正的规则缺陷：**
- 最初用“任意比典型厚度档冷一档”触发“多备保暖层”，导致夏季 30°C → 25°C 也提示需要保暖衣物。现在只有白天低至 **L4 或更冷**时才用“增加保暖层”提示，温暖但比最热天凉时不因此推荐厚外套。
- 单一主档会遗漏春季突降温：主档 L3 的五天行程也可能有白天只到 10.3°C 的 L5 日。此时继续展示主档，但必须**独立说明偏冷日如何加层**，不能只显示中位数等级。
- 典型气温靠近 6/13/18/23/28°C 的分档边界时，同时提示相邻衣物厚度选择，避免不到 1°C 的变化强迫整套换装。
- 个人“怕冷／怕热”只调整补充建议，极热仍以清凉衣物为主、严寒仍需要冬季保暖。

本轮 **8 项自动化检查通过**：数据条数、冬季积雪、春季降温/风雨、夏季不误增厚外套、秋季偏冷、温度分界连续提醒、极热/严寒的体感偏好边界、**缺少连续日期时拒绝生成误导性整段行程建议**。

**未验证/已知限制：** 目前的“典型白天”用*历史日最高温中位数*代替，可能比真正白天外出时的温度偏暖；只抽取了 26 天而非随机或全面样本；历史日雨量、阵风不说明发生时刻；本实验数据由人工转录，并没有实现天气 API 抓取、近期 14 天真实预报、未来 30 天历史多年气候模型、自动更新或线上发布。这些是后续实际接入时需要解决的事情，不应将本轮测试通过解释成穿衣舒适度或预报准确率达标。


## 7. 柏林未来 14 天预报演示：接口已由用户本机实际跑通（2026-10-14）

候选程序 `experiments/clothing-rules/forecast_advice.py` 从 [Open-Meteo Forecast API](https://open-meteo.com/en/docs) 请求柏林未来 14 个**日历日**的逐小时气温、每日降水概率/日降水量/降雪/最大阵风，按六级厚度输出旅行准备建议。仅演示，不部署、不定时运行，也不确定正式天气数据服务商。

```bash
python3 experiments/clothing-rules/forecast_advice.py
python3 experiments/clothing-rules/forecast_advice.py --preference cold
python3 -m unittest discover -s experiments/clothing-rules -p 'test_*.py' -v
```

实际运行证据：用户在 2026-10-14 19:49（Europe/Berlin）提供了成功调用真实预报 API 的程序输出，适用日期为 10 月 14～27 日，典型白天气温 14.1°C（L4），10 月 17～19 日分别 12.4/12.3/11.5°C（L5），10 月 27 日 10.4°C（L5），并有“2 天明显降水信号”的提示。因此现在可以确认**用户本地完成了一次真实接口 → 推荐结果的联网链路**。原始 Open-Meteo JSON 没有上传，无法独立重现当天的全部预报字段；也不代表预报未来一定正确。当前助手工具的网络环境仍不能直接连接该 API。

真实输出揭示的问题与本 PR 修正：

- 不再只报告最冷的 10 月 27 日，而遗漏更近的 17～19 日连续偏冷。按近期第 1～7 天、后期第 8～14 天分别展示偏冷日期段、白天气温范围和可增加的保暖层。远期降温明确要求临近复查。
- 降水和强风提醒补充具体日期，而不只显示“预计 2 天”。用户贴出的输出**未包含降水具体日期**，因此不能从那份文本反推它们是哪天。
- 运行当天若白天已经结束，明确显示“今日白天已过”；不再把当天过去时段的日降水总量当成剩余时间的天气提醒。输出标题强调 14 个日历日而非保证有 14 个未来白天。
- 天气数据的判断：用本地 09～18 时小时气温中位数代表白天气温，用 06～08 和 19～22 时段温度辅助判断早晚加层；这只是普通城市活动的近似。天气导致的保暖、挡风和防雨提醒分开，个人体感不同不意味着推荐出错。

本分支包含 2025 年柏林 26 天的历史回放样本和回放程序，以及 Open-Meteo API 格式的**合成离线测试数据**。本轮此前共 **23 项测试通过**（历史 8 项，预报 15 项），预报测试新增对用户 10 月 14 日输出中的 17～19 日冷段、27 日后期冷段、降水日期、当天已过时段和过去降水排除的回归检查。离线测试不是对实时天气服务稳定性或人体舒适度的保证。

许可：Open-Meteo Free API 仅允许非商业用途，依据其条款仍需按要求注明来源；准备商业发布之前重新核对许可或商业 API。[官方条款](https://open-meteo.com/en/terms)。

仍未完成：15～30 天长期气候参考、其他城市/任意旅行日期、网站 UI、每日定时运行与发布。此 PR 不自动授权部署或合并。

**展示边界：**
- 如果当天白天已经过去，默认建议的适用日期**从剩余有白天预报的下一个日期开始**；没有把「今日白天已过」或某个已过去日期列成用户的出行时间。
- 默认文案**不出现**「依据你提供的预报结果」；天气来源应是实际查询的 Open-Meteo，而不是用户输入。
- 日期和数值从接口数据/程序计算得到；不把手写示例文案固化进逻辑。L4 对应的衣物示例也不推断季节，因此夏季偏凉时不强称「秋季外套」。
- 厚冬装可否优先省略，只在没有明显寒冷或雪天信号的合理区间给出**温和建议**，不保证所有人的冷热感受。
- 较远日期的降温和降雨仍要提醒需要复查。默认不提供看似精确的未来一个月每日预测。
