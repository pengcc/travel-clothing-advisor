# 实际 CLI 输出 → 行李取舍：首轮质量审查

> 2026-10-15（Europe/Berlin） · Product Discovery / Problem Validation · **真实联网输出的桌面审查，不是用户效果试验**。不新增天气查询、帖子抓取、测试工具或产品代码。后续天气会变化；以下数值仅为对应时刻的快照。

## 要回答的产品问题

PR #10、#12、#11 已形成可运行的德国城市／出行日期 CLI，且用户报告完整测试 **96/96 OK**，Berlin 和 München 的实时查询成功。但**技术运行正确 ≠ 可以决定要不要带大衣**。本次审查只针对已经观察到的真实输出，判断它有没有完成项目蓝图中的 `must bring / safe to omit / wear vs carry` 决定，而不是再做一轮合成 XHS-001 A/B 文案演练。

现有依据：
- [Product Blueprint](../product-blueprint.md) 的双侧风险、全程覆盖和遗漏证据门槛。
- [PR #5 Manual Answer Test Harness](manual-answer-test-harness.md) 的五个审查维度、支持／拒绝省略规则；**未进行真人实验**。
- [XHS-001 原帖证据](xiaohongshu-evidence.md#xhs-001--看天气是十度)、[已有回答比较](xhs-001-answer-comparison.md)和[完整假设输入压力测试](xhs-001-complete-input-stress-test.md)：先前两轮桌面材料**已存在**，不重复其合成 A/B 比较。
- [室内温度／住宿研究](indoor-temperature-transit-accommodation-2026-10.md)：睡衣决定不能由室外天气单独推出。

## 观察到的两份程序输出（实际联网输入，用户转述的文本）

**A / Berlin / 2026-10-17～20；查询 2026-10-15 12:16 柏林时间**
- 白天代表气温 **12.8°C**；建议长袖＋毛衣或抓绒＋保暖程度适中的外套，轻羽绒仅为怕冷或较长早晚户外暴露时的替换选项。
- 提醒早晚更凉；“当前预报一般不必优先准备厚冬季羽绒服，但只带薄衣服也不合适”。
- 同期历史再分析：2025 年 **10.1°C**；2024 年 **15.2°C**。这是参考，不是未来预测。
- **没有**在输出中看到指定降水日，不等于整趟行程已证明不需要防雨装备。

**B / München / 2026-10-17～20；查询 2026-10-15 13:48 柏林时间**
- 白天代表气温 **13.3°C**；同样给出可穿脱的外套＋保暖中层建议。
- **10 月 18 日约 10.2°C 的偏冷白天**，提醒另备保暖层；**10 月 17 日有降水可能**，提醒雨具或防水外层；早晚更凉。
- 同期历史再分析：2025 年 **10.6°C**；2024 年 **15.2°C**。未将历史较冷年份直接当作未来一定更冷。
- “不必优先准备厚冬季羽绒服”是**低优先级建议，不等于**已证明某人的具体厚外套可安全省掉。

这些案例是对引擎**真实输出的快照**；没有保存 Open-Meteo 原始 JSON，不能核验逐日输入、历史气候统计或天气预报准确率。两份输出也**不是 XHS-001 原作者的行程**，不能把该帖的行李约束或已有衣物移植成两位真实游客的事实。

## 逐项质量审查

| 问题 | 已观察到的能力 | 尚未解决、需要避免的误读 |
| --- | --- | --- |
| 全程典型气温与变冷风险 | 两城都有选定日期和代表温度；München 点名 10/18 的 10.2°C | 只有代表值不足以断言某件外套覆盖了所有早晚／暴露 |
| 防雨与保护层 | München 10/17 给雨具或防水外层选项 | 未验证“已有软壳”确实防水，也无法由“没提示雨”推出可不带雨具 |
| **需要带什么** | 建议长袖、中间保暖层、适中外套；München 还需覆盖降水 | 没有映射为**已拥有衣物**的最小组合，也没有确认多件是否重复 |
| **什么可以省** | 厚冬季羽绒服暂不优先，避免“德国＝全带冬装” | 并未说明可否不带**那件具体大衣**；缺保暖性能、外出暴露和行李约束，不能标成 `safe to omit` |
| **出发穿／白天带** | 提到分层及随时穿脱 | 缺一项具体动作：哪件出门穿、气温回升时哪件进小包；也不知道日包空间 |
| **室内／睡衣** | 当前天气输出没有擅自推荐厚睡衣（合理） | 酒店是否供暖、房间温度可否控制仍未知；不能以 10°C 室外温度断言睡衣厚度 |
| 历史与不确定性 | 历史与预报区分，提到重新查询 | 两年同期不可作为“漏带风险概率”，不应仅因某年较冷额外堆衣物 |

**本轮判断（桌面审查）：** 引擎已能提供具备实际条件依据的**防护方向**，但尚未完成“只带手提箱的大衣保留／替代／省略”这类**具体物品取舍**。这不是引擎坏掉；它当前没有旅客已有衣物能力和空间数据。不能把输出条数增加等同于决策改善，也不能假定更长的历史清单能解决取舍。

## 最小的下一次输出实验：用同一组事实回答一个选择题

**只在现有两份真实快照上进行一次人工“决策摘要”试写**，不修改天气引擎，不声称已改善真人打包结果，也不增加新的城市／天气／人口样本。每条候选答案应维持当前输出的天气事实，并控制在简短范围内。

建议候选答案的四个部分（不是固定 UI 合同）：
1. **先覆盖什么**：例如 Berlin 的保暖内层＋适中外层；München 另外明确 10/17 防雨、10/18 更冷。
2. **可以暂不优先什么**：例如厚冬季羽绒服“在这些预报和一般城市活动条件下不是首选”，与“已确认可以安全省掉某件大衣”严格区分。
3. **白天穿与随身带**：明确建议可脱的中间层随身携带，但**不能**假定用户有足够日包空间。
4. **最小信息缺口**：若用户问“我的大衣和软壳留哪件”，只询问真正会改变取舍的衣物性能／户外活动／空间信息；若缺信息则给条件性判断，不虚构衣物参数。

### 候选决策摘要（仅用于审查，不是更精确的新预报）

**Berlin（以上 12.8°C 预报快照）：** 这几天优先保证长袖、可脱的毛衣／抓绒和一件适中外套能组合使用。厚冬季羽绒服不是当前预报下的首选，但如果你早晚长时间在外或很怕冷，需要复核保暖能力。白天变暖时可脱中层，脱下的衣物仍需要收纳。**目前没有你的大衣／外套性能或活动安排，不能断言具体哪件可以安全不带。**

**München（以上 13.3°C 预报快照）：** 在同样的分层组合外，还要覆盖 10/17 的可能降雨，以及 10/18 约 10.2°C 的偏冷白天：雨具或已确认防雨的外层与一件可加的保暖层是两种不同功能。不要仅因“有雨”就机械地再带第二件大衣，也不要把未经确认防雨的软壳当作一定防水。早晚用保暖层，暖些时脱下并随身收纳；**没有已有衣物及户外暴露资料，不能替你决定删掉哪件外套。**

以上与程序实测文案有相同天气事实，但更明确说明**该覆盖什么能力、该留待决定什么**。这只证明可以写出这样的答案，**不证明更易懂、决策更好或差异化成立**。

## 决策门槛与下一次动作

- **可以从现有数据直接判定的：** 对应四天需要覆盖保暖层／外层；München 的 10/17 需要关注雨具、10/18 需考虑增加保暖层；不优先考虑厚冬季羽绒服是当前预报下的**条件性建议**。
- **当前不能直接判定的：** 某个人那件大衣、背心、软壳是否可安全省掉；是否有空间装下；某家酒店是否需厚睡衣；历史两年是否“足够证明以后也差不多”。
- **优先完成的下一次产品改动：** 在保持现有预测／等级不变的前提下，让 CLI 的用户摘要优先交代“要覆盖的能力、条件性不优先项、穿／带提示”，并为无法判断具体省略的情况留出明确出口。**先评审这一输出语义**，再决定是否为真实用户衣物列表增加最小输入；不因代码已可运行就默认应建设网页。
- **一个明确可证伪的检验：** 当旅行者已经指定“带不带这件大衣”及自身可替代衣物时，候选输出能否给出**具体的保留／替换／尚不能省**理由，且不会在缺乏真实能力证据时宣称安全省略。若仍然只是更长的泛泛层次清单，就不值得引入新模式。
- **后续用户反馈的条件：** 只有遇到真实打包问题才使用现有 [PR #5 harness](manual-answer-test-harness.md) 记录基线、阅读后具体增减与反事实误读；不用募集人或追加小红书帖子作为完成本次审查的前提。无真人决定结果时，始终写“未观察”，不报效果指标。
