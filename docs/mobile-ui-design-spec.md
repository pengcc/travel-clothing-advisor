# Travel Clothing Advisor — Mobile UI Design Specification (V1)

> **状态：** 待 Review 的设计规范 · 2026-10-15；不是已发布网页。  
> **功能来源：** [MVP Functional & Technical Specification](mvp-functional-technical-spec.md)。  
> **已定方向：** Mobile-first；**旅行计划查询与精选城市完全独立**；C「轻快友好」奶油白＋陶土橙＋浅沙色；结论先于气温解释。

## 1. 两个独立入口，不共享查询状态

| | 按行程查询 | 精选城市 |
| --- | --- | --- |
| 用户目的 | 为自己确定日期的旅行准备行李 | 不填表，直接浏览城市今起 14 天的穿衣参考 |
| 输入 | 用户选城市、到达/离开日期及体感 | 点击城市；无需任何输入 |
| 固定范围 | 德国当地今天至 +29 天；14 天之外为 5 年同期历史参考 | 德国当地**今天至今天+13 天，含今天**，每天按实际天气数据更新 |
| 体感 | 怕冷 / 一般（默认）/ 怕热 | 固定「一般」 |
| 结果页标识 | 「行程穿衣建议」 | 「城市穿衣参考」 |
| 返回 | 「修改行程」，保留表单全部输入 | 「返回精选城市」，保留另一入口的表单不变 |
| 分享链接 | `?view=trip&city_id=...&start=...&end=...&preference=...`，以所选参数重算 | `?view=city&city_id=...`，按德国当地重新打开当天起 14 天、体感一般；不包含私人行程参数 |

**不可出现的行为**：点击精选城市就预填/提交上方行程表单，套用用户选过的日期/体感，或者要求填写日期才能看城市建议。两个入口可以复用穿衣卡片**组件**，但不得混用输入状态。进入任一结果、返回及浏览器前进/后退都要保持这种隔离。

## 2. 文案原则和推荐字词

- **先回答「带多厚」**：将外套类型写清楚，再说明内搭与需要临时穿脱的层次。避免只有「请注意保暖」「适度增减衣物」等无法实际指导打包的句子。
- **一句只回答一个问题**：标题/按钮尽量短；不要一段里同时讲数据模型、体感偏好和温差。
- **气温数据必须有身份**：14 天内叫「气温预报」，超出窗口叫「往年同期气温参考」；历史结果清楚声明「不是这次旅行的天气预报」。气温是依据，不能伪装成确定的穿衣效果。
- **不夸大服务**：避免「精准」「保证不冷」「实时更新」「每天准时更新」；如预取失败，不能继续写「今日已更新」，只显示实际数据时间/状态。
- **不使用户误解城市卡片与个人计划有关**：两个区块名称、按钮、页面标题、返回按钮和分享链接都独立。长文案优先自然口语，不写气象报告式结论。

## 3. 页面信息层级

**首页（先查询，再浏览）**：站点标识 → 一句问题型主标题与说明 → 「按行程查询」表单（目的地、到达/离开日期、体感）和一个主按钮 → 独立的「精选城市」标题、14 天范围与实际更新时间 → 10 城卡片/分页。二者为并列功能，视觉上用间距或细分隔线区分，不使用「也可以」之类暗示同一操作流程的说法。

**行程结果**：修改行程 → 「行程穿衣建议」＋城市及**用户指定**日期/体感 → 预报/历史资料标签 → 大字号外套结论 → **冷热变化提醒（仅 `packing_variation_notice` 非空时，紧跟外套结论）** → 内搭 → 早晚提醒 → 来源、数据时间及不确定性 → 复制建议/链接。

**精选结果**：返回精选城市 → 「城市穿衣参考」＋城市及**今起14天实际日期范围**＋「一般体感」 → 气温预报标签 → 大字号外套结论 → **冷热变化提醒（仅 `packing_variation_notice` 非空时，紧跟外套结论）** → 内搭 → 早晚提醒 → 来源、数据时间及不确定性 → 复制建议/城市参考链接。**不显示用户旅行计划日期、不出现「修改行程」**。

预报结束于德国今天+13日；若行程超出此日期、但仍在 30 天范围内，整个行程统一用 5 年 ERA5 同期参考。结果卡片结构保持一致，模式及不确定性文字必须不同。不得将历史参考显示为未来逐日精确天气。

### 保暖标记：临时用信号格，正式视觉独立迭代

**当前可用方案**：保留已有的「五格递增短条＋中文名称」小型胶囊标记作为临时实现，不再单独放「保暖标记 · 5 档视觉对照」或刻度说明区。用户**必须直接从同一标记上的中文文字和穿衣建议理解意义**，不应为了看懂标记再学习图例。标记只是快速提示，不是天气温度值或整个行程冷热范围的完整描述。**跨日冷热变化提醒与主等级标记各自独立**：即使主等级明确（例如 L2→L4→L2），也须显示重要提醒；只有没有代表性的主等级时才用「冷热变化大」代替刻度，不能因有主等级而隐藏温差。

| 后端六档 | 临时标记文字 |
| --- | --- |
| L1 / L2 | 轻薄 |
| L3 | 薄外层 |
| L4 | 适中保暖 |
| L5 | 加强保暖 |
| L6 | 冬季保暖 |

- 使用独立、可替换的 `WarmthIndicator` 展示组件；从 API/精选城市快照读取**必有的 `warmth_indicator_level: 1..6 | null`**。非空值按上表映射中文标签和临时图形，`null` 时只显示「冷热变化大」文字、**不展示虚构的单一主档位**。该值由服务端模型决定，前端不重算；临时图形沿用现有颜色与五格刻度，**不作为品牌视觉定稿**。**变化提醒由独立 `packing_variation_notice` 驱动，不从 `warmth_indicator_level` 推断或强行与 `null` 绑定。**
- 正式品牌设计另行专项探索：例如有辨识度、富有一点动感的小动物（螃蟹是候选），使用姿态、穿着与表情表达冷暖，但必须**在城市小卡片上直接可辨认**，不需要旁边配五档图例。是否最终采用动物仍待验证。
- 将标记放在精选城市卡片和两类结果页，但整页品牌配色保持奶油白／陶土橙；徽记不替代「具体带什么外套」的主句，也不为了图标设计延迟 MVP。辅助技术能读出等级名称。
- **跨度大的行程**：标记只代表有意义的主档次；**预报模式**若某一天偏冷或偏暖且影响备衣，就用独立提醒写明该天应备或可脱的层次；**历史参考模式**只描述过去五年样本支持的冷热备衣风险，不把某个历史日期当作这次旅行的预报。没有代表性主档才切换成「冷热变化大」文字，不能把这个显示状态当作温差触发条件。

### 冷热变化与历史备衣风险：哪怕一天，也要突出真正影响打包的条件

**目的**是防止用户漏带较冷情况需要的外套／保暖层，或明显偏暖时无法脱去厚衣物。这里是穿衣参考，不是高温／寒冷天气预警，也不是逐日指定穿搭。预报模式中**一天也可能决定是否需要多带一件衣服**，不要求达到某个天数或占比；历史模式不能断言此次旅行会在某一天发生过去的冷暖状况。

**触发原则**：由服务端根据有效气温是否改变备衣决定生成 `packing_variation_notice`（简短字符串或 `null`），不由 UI 重算。**预报模式**逐日比较，跨两档如 L2→L4→L2、L4→L2→L4 是典型场景；即使只有一天明显偏冷或偏热也提醒，不能要求多档各出现多天，也不能按中位数代表性决定是否提醒。**历史模式**比较五年对应窗口中确有依据的冷暖与外套需求差异，只能说明「过去五年同期曾出现……，建议……」，**不能把历史日期写成未来会发生的偏冷／偏暖日**。只有阈值边缘轻微波动且备衣需求不变时不夸大；没有有意义差异则为 `null`。

**结果页面信息优先级**：

1. **主穿衣结论**：直接说通常需要多厚的外套；若冷热分化严重、没有代表性主档位，`warmth_indicator_level`／`reference_temperature_c` 可为 `null`，但**不能只写「方便增减衣物」**，必须根据有依据的较冷需求明确最需要考虑的外套厚度、保暖内搭，以及偏暖时可减薄的选择。例如五年历史样本确实覆盖 L2 暖天与 L6 冬季寒冷风险时，应写「历史同期曾出现需冬季保暖外套和保暖内搭的偏冷情况；较暖时可换薄长袖」，而不是把中位数或 L3 误当成「大部分日子」的穿法。此话不是断言未来必定寒冷。
2. **醒目的「冷热变化／备衣风险提醒」**：仅在 `packing_variation_notice` 非空时显示，**直接紧跟主外套结论，在普通内搭解释、早晚提醒、数据来源之前**。使用一块紧凑的淡沙／浅陶土色背景、细边框、简明标题与可辨识的小图标（如上下箭头）；**预报模式**可标出有依据的偏冷／偏暖日期与应多备／少穿的层次，**历史模式**则写过去五年同期实际观察到的冷暖备衣风险及相应外套／内搭，不写「某未来日期将偏冷」。至少文字明确，不能只靠颜色／图形。不要使用大面积刺眼红色、警报铃、弹窗或重复警告。
3. **补充解释**：早晚偏冷、远期不确定性等只在有关时附一两句；与独立的冷热提醒是不同情形。第 8–14 天用「可先备一层，临近出发再确认」等谨慎措辞；5 年历史模式始终注明「历史同期参考，不是此次旅行的天气预报」，不虚构未来具体冷暖日期。

**精选城市卡片**：在主要衣物结论下，读取预取快照的 **`packing_variation_summary: string | null`**；非空时显示服务端生成的**一句简短、完整的提醒**，例如「有一天偏冷，建议多备一层」。与结果页的完整 `packing_variation_notice` 依据**同一次逐日判断**生成：有重要冷热变化，两处都非空；没有变化，两处都为 `null`。卡片不用前端温度判断、截断结果页长文或补写另一套建议。窄屏/字号放大时允许换行，不能以省略号截断关键意思。完整日期和备衣建议在城市结果页提供；卡片不增加第二张提示卡、复杂图表或五档图例。信号格仍可正常显示主档位，不必等 `warmth_indicator_level=null` 才显示变化提示。

**用于评审的预报假设场景（非真实天气）**：

| 有效的 3 天白天气温 | 页面应重点提醒 |
| --- | --- |
| L2（24°C）→ L4（14°C）→ L2（24°C） | 「第2天明显偏冷，建议额外备一件适中外套或可叠穿的保暖层；其他两天轻薄即可。」同时可显示主要 L2 档位 |
| L4（14°C）→ L2（24°C）→ L4（14°C） | 「第2天明显偏暖，注意内搭可以更轻薄，外套方便脱下。」同时可显示主要 L4 档位 |
| 7 天 L2、7 天 L4，中位数落在无人出现的 L3 | 不声称多数天为 L3；主标记可为 `null`，但温差提醒仍须独立显示 |
| 稳定单档，或只有接近阈值的细小波动 | 不显示额外的跨日期冷热变化提醒 |

**历史参考独立验收场景（合成样本）**：五年同期样本在较暖时相当于 L2、在可信较冷情况相当于 L6，且没有可解释的单一主档时：主保暖标记与代表气温可为 `null`，但主句仍须明确「冬季保暖外套、保暖内搭，暖时减薄」；`packing_variation_notice` 可描述「过去五年同期曾出现需要冬季外套的偏冷情况」，不得写「11 月 23 日将偏冷」。如果五年同期样本没有影响备衣的差异，提醒为 `null`，不能为了显示提醒而编造风险。

建议包含城市实际查询的日期或原始气温时必须有数据依据；**预报日期和历史证据来源必须明确区分**。**最终组合由用户自己决定**，目标是避免忘带关键的一层，而非生成每天的精确穿搭。

## 5. 排版、间距与控件

- 中文系统字体，优先 `-apple-system, BlinkMacSystemFont, "PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC", sans-serif`；不必下载在线中文字体。
- 手机主标题约 30px/1.25，穿衣结论 24px/1.35，区块标题 20px/1.35，正文 16px/1.55，字段名 14px，来源/更新时间 13px；字体放大允许换行，不裁切关键句。
- 间距基数 4/8/12/16/24/32px；页面两侧 16px，卡片内部 16px，区块之间 24–32px。圆角 12–16px，优先留白和细边框，不做大量阴影。
- 主按钮、日期入口、城市卡片等可点击区域至少 44px；输入字号 16px，键盘焦点清楚可见。
- 手机 320/375/390/430px 为优先评审宽度。两日期字段在窄屏不可读时纵向排列；卡片可从两列变一列。桌面主内容最大宽度约 1040px，查询表单不拉伸至整屏。

## 6. 主要交互和必要状态

- **按行程查询**：城市从建议列表选取，同名地点显示德国联邦州；日期区间允许德国今天至 +29 日，结束不早于开始；体感默认一般；查询中防重复点击，失败保留输入。
- **精选城市**：首页卡片点击后直接得到城市独立结果；读取预取的 14 天数据，不由个人行程控制，固定一般体感。城市浏览/分页不触发天气 API；**预取快照的卡片**读取服务端 `warmth_indicator_level`（允许 `null`）与 `packing_variation_summary`（允许 `null`）；**独立结果页**读取同一模型得出的 `warmth_indicator_level` 与较完整的 `packing_variation_notice`（允许 `null`）。快照与结果在相同德国日期、天气数据版本和有效预测时段下不应互相矛盾；若当天部分时段已过去或预报已刷新，结果可按当前有效时段重新计算，并明确实际计算/更新时间，不能把过去天气当未来。 「今起14天」指含今天的14个德国日历日；如果当天白天已过，不将过去的白天当作仍可预测的未来时段。
- **返回及链接**：可独立返回，浏览器前进/后退正确区分「行程」和「城市参考」；应用区分 `view=trip`（城市 ID、起止日期、体感）与 `view=city`（仅城市 ID）；城市链接按访问时德国当地今天至 +13 天、体感一般重算，跨日验证缓存有效性。不把旧日期/私人体感带入城市参考，不需要新增独立天气 API。
- **异常状态**：城市不存在/同名、日期无效、数据加载中、首页快照缺失、数据已过期、上游超时/失败、历史数据不足、长句断行、无障碍大字模式。无依据时**绝不生成看似真实的穿衣结论**；过期状态保留原日期与更新时间。
- **演示原型**：所有气温和衣物举例明确标记「演示数据，非真实天气」；不伪造 Open-Meteo 更新时间或用户所在城市天气。

分别验证：①行程自定义日期/体感只影响行程结果；②点击精选城市直接显示该城市**今起14天、一般体感**且不改变行程输入；③两种结果、返回、分享参数及跨德国当地午夜重算均正确；④超过14天的行程标为历史参考；⑤**三天 L2→L4→L2 时哪怕仅一天偏冷也在主结论下面醒目提醒，同时可以保留 L2 主标记；反向 L4→L2→L4 也提醒偏暖一天、方便穿脱；7 天 L2 + 7 天 L4 不把中位数 L3 说成多数天，单一等级缺乏代表性时可为 `null`**；⑥稳定单档或边界附近细小波动没有多余提醒；⑦结果页的跨日变化提醒优先于内搭、早晚说明，精选城市卡片只读取服务端的简短 `packing_variation_summary`，与结果页的 `packing_variation_notice` 同步触发、不截断关键意思；在 320/375/390/430px 和大字模式均可正常阅读、屏幕阅读器可识别，且不与早晚温差和远期不确定性重复；⑧无数据或历史模式不编造未来具体冷暖日期。以完整实际中文句子验收，而不只检查占位文字。
