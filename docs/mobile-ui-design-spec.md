# Travel Clothing Advisor — Mobile UI Design Specification (V1)

> **状态：** 待 Review 的设计规范 · 2026-10-15；不是已发布网页。  
> **功能来源：** [MVP Functional & Technical Specification](mvp-functional-technical-spec.md)。  
> **已定方向：** Mobile-first；**旅行计划查询与精选城市完全独立**；C「轻快友好」奶油白＋陶土橙＋浅沙色；结论先于气温解释。

## 1. 两个独立入口，不共享查询状态

| | 按行程查询 | 精选城市 |
| --- | --- | --- |
| 用户目的 | 为自己确定日期的旅行准备行李 | 不填表，直接浏览城市今起 14 天的穿衣参考 |
| 输入 | 用户选城市、到达/离开日期及体感 | 点击城市；无需任何输入 |
| 固定范围 | 德国当地今天至 +29 天；14 天之外为 8 年同期历史参考 | 德国当地**今天至今天+13 天，含今天**，每天按实际天气数据更新 |
| 体感 | 怕冷 / 一般（默认）/ 怕热 | 固定「一般」 |
| 结果页标识 | 「行程穿衣建议」 | 「城市穿衣参考」 |
| 返回 | 「修改行程」，保留表单全部输入 | 「返回精选城市」，保留另一入口的表单不变 |
| 分享链接 | 重算该用户给定参数 | 重算该城市当日的默认 14 天窗口；不能附带私人行程参数 |

**不可出现的行为**：点击精选城市就预填/提交上方行程表单，套用用户选过的日期/体感，或者要求填写日期才能看城市建议。两个入口可以复用穿衣卡片**组件**，但不得混用输入状态。进入任一结果、返回及浏览器前进/后退都要保持这种隔离。

## 2. 文案原则和推荐字词

- **先回答「带多厚」**：将外套类型写清楚，再说明内搭与需要临时穿脱的层次。避免只有「请注意保暖」「适度增减衣物」等无法实际指导打包的句子。
- **一句只回答一个问题**：标题/按钮尽量短；不要一段里同时讲数据模型、体感偏好和温差。
- **气温数据必须有身份**：14 天内叫「气温预报」，超出窗口叫「往年同期气温参考」；历史结果清楚声明「不是这次旅行的天气预报」。气温是依据，不能伪装成确定的穿衣效果。
- **不夸大服务**：避免「精准」「保证不冷」「实时更新」「每天准时更新」；如预取失败，不能继续写「今日已更新」，只显示实际数据时间/状态。
- **不使用户误解城市卡片与个人计划有关**：两个区块名称、按钮、页面标题、返回按钮和分享链接都独立。长文案优先自然口语，不写气象报告式结论。

### V1 推荐微文案（直接用于页面）

| 位置 | 推荐文案 | 避免 |
| --- | --- | --- |
| 站点名称 | **旅途穿衣** | 冗长的英文技术名称 |
| 首页主标题 | **去德国，衣服带多厚？** | 「智能精准天气穿搭预测」 |
| 主标题说明 | 选好目的地和日期，看看外套、内搭怎么准备。 | 「全面解决所有天气问题」 |
| 表单标题 | **按行程查询** | 「精选城市查询」 |
| 城市字段 | 目的地；占位「例如：柏林 Berlin」 | 「输入经纬度」 |
| 日期字段 | 到达日期 / 离开日期 | 「预测开始/结束」 |
| 体感问题 | **你平时更怕冷还是怕热？** | 「体温敏感性模型」 |
| 体感选项 | 怕冷 / 一般 / 怕热 | 复杂人群分类 |
| 表单主按钮 | **查看行程建议** | 「查看精选城市」 |
| 城市区块标题 | **精选城市** | 「你的推荐城市」 |
| 城市区块说明 | **点开城市，直接看今起14天的穿衣参考。** | 「请选择城市并填写日期」 |
| 城市卡片动作 | **查看14天建议 →** | 「填写旅行日期」 |
| 行程结果标题 | **行程穿衣建议** | 「14天城市概况」 |
| 精选结果标题 | **城市穿衣参考** | 「你的旅行计划」 |
| 结果主标签 | **外套建议** | 「最重要的衣物建议」；「一定要带外套」 |
| 内搭标签 | **里面怎么穿** | 「分层穿衣策略详解」 |
| 行程返回 | **修改行程** | 「返回城市列表」 |
| 精选返回 | **返回精选城市** | 「修改行程」 |
| 分享 | **复制建议** / **复制链接** | 「分享实时精准预报」 |
| 预报数据说明 | 行程：**依据所选日期的气温预报**；精选城市：**依据今起14天的气温预报**。均显示实际数据更新时间 | 「保证本次旅行天气准确」 |
| 历史数据说明 | **依据：过去8年同期气温。这是提前备衣参考，不是旅行当天的天气预报。** | 「预计11月某天一定是X°C」 |
| 无数据 / 查询失败 | **暂时无法获取气温数据，请稍后重试。** | 填充未经计算的衣物建议 |

**文案随结果改变**：上表中的衣物名称和提醒是表达原则，不是固定的温度—衣物对应表；具体外套、内搭及提醒仍由既有 Python 衣物模型产生。首页卡片应以具体外套结论为主，最多附一条真正影响穿衣的提醒。

## 3. 页面信息层级

**首页（先查询，再浏览）**：站点标识 → 一句问题型主标题与说明 → 「按行程查询」表单（目的地、到达/离开日期、体感）和一个主按钮 → 独立的「精选城市」标题、14 天范围与实际更新时间 → 10 城卡片/分页。二者为并列功能，视觉上用间距或细分隔线区分，不使用「也可以」之类暗示同一操作流程的说法。

**行程结果**：修改行程 → 「行程穿衣建议」＋城市及**用户指定**日期/体感 → 预报/历史资料标签 → 大字号外套结论 → 内搭 → 早晚提醒 → 来源、数据时间及不确定性 → 复制建议/链接。

**精选结果**：返回精选城市 → 「城市穿衣参考」＋城市及**今起14天实际日期范围**＋「一般体感」 → 气温预报标签 → 大字号外套结论 → 内搭 → 早晚提醒 → 来源、数据时间及不确定性 → 复制建议/城市参考链接。**不显示用户旅行计划日期、不出现「修改行程」**。

预报结束于德国今天+13日；若行程超出此日期、但仍在 30 天范围内，整个行程统一用 8 年 ERA5 同期参考。结果卡片结构保持一致，模式及不确定性文字必须不同。不得将历史参考显示为未来逐日精确天气。

## 4. 配色与可读性

| Token | 色值 | 用法 |
| --- | --- | --- |
| `--color-page` | `#FFF9F4` | 奶油白页面 |
| `--color-surface` | `#FFFFFF` | 白色表单/卡片 |
| `--color-ink` | `#3D302A` | 标题和正文 |
| `--color-muted` | `#74665E` | 辅助说明 |
| `--color-brand` | `#C96849` | 陶土橙图标/点缀；不与白色小字叠加 |
| `--color-action` | `#A64E35` | 主按钮、交互文字 |
| `--color-selected` | `#F4DBCF` | 选中背景、温和提示 |
| `--color-sand` | `#E8D6B9` | 浅沙背景，少量使用 |
| `--color-line` | `#EADFD5` | 细边框 |

计算对比度：主按钮白字 ≈ 5.58:1；正文/奶油白 ≈ 12.15:1；辅助文字/奶油白 ≈ 5.29:1；**浅陶土橙 `#C96849` 配白字仅约 3.78:1，不用于普通字号文字**。颜色不能作为已选、报错或过期的唯一提示。

## 5. 排版、间距与控件

- 中文系统字体，优先 `-apple-system, BlinkMacSystemFont, "PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC", sans-serif`；不必下载在线中文字体。
- 手机主标题约 30px/1.25，穿衣结论 24px/1.35，区块标题 20px/1.35，正文 16px/1.55，字段名 14px，来源/更新时间 13px；字体放大允许换行，不裁切关键句。
- 间距基数 4/8/12/16/24/32px；页面两侧 16px，卡片内部 16px，区块之间 24–32px。圆角 12–16px，优先留白和细边框，不做大量阴影。
- 主按钮、日期入口、城市卡片等可点击区域至少 44px；输入字号 16px，键盘焦点清楚可见。
- 手机 320/375/390/430px 为优先评审宽度。两日期字段在窄屏不可读时纵向排列；卡片可从两列变一列。桌面主内容最大宽度约 1040px，查询表单不拉伸至整屏。

## 6. 主要交互和必要状态

- **按行程查询**：城市从建议列表选取，同名地点显示德国联邦州；日期区间允许德国今天至 +29 日，结束不早于开始；体感默认一般；查询中防重复点击，失败保留输入。
- **精选城市**：首页卡片点击后直接得到城市独立结果；读取预取的 14 天数据，不由个人行程控制，固定一般体感。城市浏览/分页不触发天气 API。
- **返回及链接**：可独立返回，浏览器前进/后退正确区分「行程」和「城市参考」；行程分享含城市/起止日期/体感，城市分享只包含城市及城市参考模式，重新打开时采用当天14天窗口。
- **异常状态**：城市不存在/同名、日期无效、数据加载中、首页快照缺失、数据已过期、上游超时/失败、历史数据不足、长句断行、无障碍大字模式。无依据时**绝不生成看似真实的穿衣结论**；过期状态保留原日期与更新时间。
- **演示原型**：所有气温和衣物举例明确标记「演示数据，非真实天气」；不伪造 Open-Meteo 更新时间或用户所在城市天气。

## 7. 验收边界与下一步

分别验证：①行程自定义日期/体感只影响行程结果；②点击任何精选城市都直接显示该城市**今起14天、一般体感**且不改变/读取行程输入；③两种模式的标题、返回、分享参数均正确；④超过14天的个人行程标为历史参考；⑤上述异常状态及手机窄屏阅读。使用自然的中文完整文案和较长的穿衣句子，而不是仅用设计占位符。

下一步先审查两入口与文案的**可点击 Mobile-first 原型**，再讨论是否需要视觉微调。此 PR 仅维护 UI 与必要产品规格，不添加实际天气 API/用户账户/生产部署。
