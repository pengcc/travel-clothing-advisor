# Issue #41 — Safari trip calendar and date-range implementation plan

**Status:** Proposed for independent Plan Review; **documentation only; not approval to implement**.
**Target:** [Issue #41](https://github.com/pengcc/travel-clothing-advisor/issues/41), parent [#38](https://github.com/pengcc/travel-clothing-advisor/issues/38). Repository evidence inspected on `main` at `71990ae25cf3cf21c1b5952135782223515a1a18`.

## Outcome and selected UX approach

Travelers can choose a German-local arrival and departure date without guessing which dates are available, opening the wrong month, or discovering an invalid order only at submission.

**Choose a small project-owned vanilla-JS calendar, not another native `type=date` workaround.** The current Safari/native UI does not reliably communicate the enabled range or control the opened departure month; setting `min` alone does not meet the observed need. Do not add React, a general UI framework, external CDN, or weather/packing logic to the date component. Implement one shared calendar **dialog** for the two existing date fields, with editable `YYYY-MM-DD` text inputs for direct keyboard entry and adjacent labeled calendar buttons. Preserve `#start`/`#end` as the canonical ISO-valued form controls, so state, return/edit, and existing URL contracts remain usable.

- **Arrival first:** show the current eligible month, or the current valid arrival's month. When a date is selected, show it immediately; if no valid departure remains, continue in the same calendar to select departure.
- **Departure:** cannot be selected before valid arrival. Open at the selected arrival's month (or an existing valid departure's month), not blindly at today's month. The eligible end interval is `[start, min(start+29 days, today+59 days)]`. If arrival changes, keep departure **if still in this interval**; otherwise clear it, explain why, and offer departure selection. Temporary partially typed arrival input must not silently erase a previously valid departure; validate on commit/submit.
- **Visible states:** distinctive today, arrival, departure, inclusive selected interval, disabled dates and keyboard focus; weekday headings, localized month/year and clear previous/next month buttons. Never make a disabled day look selectable. Show a concise range/duration hint outside the popup too.
- **Accessibility:** use an actual labeled dialog with correct focus containment/return and screen-reader month announcements; calendar grid with one tab stop, arrow/week navigation, Home/End, PageUp/PageDown, Enter/Space to select, Escape to close. Accessible full-date labels, `aria-selected` and disabled semantics must match displayed state. Keep text entry, error association, focus-visible, touch targets, responsive 320px/mobile and reduced-motion behavior. Reference the [W3C APG date-picker dialog example](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/) as a behavioral guide, **not production-ready code**; manually verify Safari/iOS and assistive technology.

## Product-rule decision gate (must be explicitly accepted before implementation)

**Candidate, not yet authorized:** the whole valid personal trip stays within **60 German-local calendar dates, inclusive**: `today <= start <= end <= today+59 days`; maximum trip length is **30 dates inclusive**: `(end-start).days+1 <= 30`. Thus arrival may be as late as day 60, but an end date never exceeds day 60; arrival on the last date permits a one-day trip. One-day trips remain valid. The current query horizon is only 30 dates; extending it is a product change and must pass review plus explicit acceptance, not just a calendar-`max` edit.

Suggested user wording: **“可查询德国当地今起60天内的行程，单次最长30天。”** Separately explain: **“整趟行程都在今起14天预报范围内时使用预报；超出则整趟使用过去五年同期气温参考，并非出行日天气预报。”** Never call a short trip beginning 40 days from now a “15–30天行程”.

Keep `forecast_end=today+13` and 14-day forecast source semantics untouched. If `end > forecast_end`, route **the entire trip** to five complete analogous historic windows, not a forecast/history mixture. Missing, recent-unpublished, or corrupt historical months still fail closed with their existing preparation/unavailable result; this task does not build automatic backfill.

## Implementation slices and actual paths

1. **Canonical backend limits:** centralize query-horizon (candidate 60), max-trip-duration (30), forecast horizon (14) at the existing `web/fixtures.py`/shared window boundary. Return authoritative `today`, `forecast_end`, `max_date` through `/api/context`; apply the **same** strict ISO-date and inclusive-duration validation in fixture `web/fixtures.py::validate` and live `web/live.py::Service.advice`. Keep API rejection authoritative even for manually authored/deep links; distinguish invalid date/sequence/horizon/duration in Chinese errors without leaking provider details. Do not expand featured-city date semantics.
2. **Calendar UI:** add `web/static/trip-calendar.js` for date-only arithmetic, dialog/grid UI, keyboard behavior, and a single source of start/end constraint state. Adjust `web/templates/index.html` for labeled editable date inputs, calendar triggers, help/error descriptions, and the dialog host; add only this script to `web/server.py`'s explicit static allowlist. Scope `web/static/style.css` to calendar states and responsive overlay. In `web/static/app.js`, replace both native min/max assignments with calendar syncing on `refreshContext`, committed edits, `restoreForm`, return/back/forward, fixture toggle, and Germany-midnight refresh. Validate before navigation and show field-level error/focus, not an incorrect default date.
3. **Historical preparation alignment:** `web/history.py::plan` currently iterates 30 arrival dates and assumes `end=today+29`; update its **offline planning set only** to consider all 60 eligible starts with each allowed end bounded by `min(start+29,today+59)`. Retain `web/history.py::windows`' **30-day duration** guard, existing five-year arrival-year anchoring, Feb-29 fallback and continuous cross-year dates. Keep `web/prefetch_history.py` read-only check, quotas, download admission, cache identity, worker behavior and provider IO otherwise unchanged. No bulk download.
4. **Text/compatibility:** update the currently misleading “15–30天参考” homepage explanation and relevant `web/README.md`, `docs/mvp-functional-technical-spec.md` (and status facts in `docs/product-blueprint.md` if needed), but **only after** the product rule has been accepted. Preserve strict duplicate-parameter and `view=city` URL handling, personal form restoration, and result/copy wording. Do not migrate/reset existing history or forecast cache objects; old shared trip URLs must be revalidated under the **current** German date and new bounds, not silently adjusted.

## Required offline/real-device verification

- **Date math / API:** today and day +59 accepted; day +60 rejected; one day and 30 inclusive accepted; 31 rejected even inside 60; end before start; malformed and impossible ISO dates; absent values; duplicate link params; both fixture and live API return 400 rather than contacting weather services on invalid input.
- **Mode/history:** end at +13 => whole-trip forecast; end at +14 => whole-trip five-year reference even for a two-day trip; no mixing. Cross-year arrival `2026-12-29..2027-01-03`, leap-day arrival `2028-02-29`, leap-day spanning and missing/incomplete history. `plan()` includes required mapped months for late-window starts without exceeding 30-trip-days. No new download/caching decisions here.
- **Calendar interaction:** select arrival next month, then departure opens the relevant month; end-before-start and >30-day/end-of-horizon dates disabled; valid existing departure preserved on editing start; newly invalid departure cleared; empty/partially typed/invalid dates prompt without fabricated selections; date interval/today/disabled styles remain distinguishable; year/month navigation and keyboard/focus/ARIA work.
- **State and boundary:** fixture/live switching, browser back/forward and reload, city-card navigation not overwriting personal trip, link sharing, German midnight and DST rollover (including stale form/date context), historic snapshot failures preserving editable inputs, mobile overflow at 320/375/390/430px, long labels and large text.
- **Commands:** run `python3 -m unittest discover -s tests/web -v` and `python3 -m unittest discover -s experiments/clothing-rules -q`; extend `tests/web/test_ui.py`, `tests/web/test_live.py`, `tests/web/test_history.py` / `test_history_operations.py`; update existing date-input interactions in `tests/web/browser.cjs`, `history-browser.cjs` and related regression scripts. Add one deterministic browser calendar regression against the loopback fixture server. Run other existing browser regressions touched by state changes. **Real Safari desktop and iOS Safari**, Chrome desktop/mobile, keyboard and at least VoiceOver on Safari require actual interactive verification; Chromium/Playwright alone cannot claim Safari acceptance. Capture results and exceptions.
