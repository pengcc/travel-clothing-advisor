# Travel Clothing Advisor — MVP Functional & Technical Specification

> **版本：** V1 目标规格（待 PR 审阅/合并） · 2026-10-15  
> **范围：** 德国旅行穿衣建议网站的功能、输入输出、天气数据、缓存和部署；**不是 UI 视觉设计稿，也不是已实现功能**。  
> **依据：** 用户在 2026-10-15 的产品取舍；现有 `main` 上 PR #14 的 Python 原型。

## 1. 产品目标与边界

帮助不熟悉德国天气的旅行者回答：**旅行时需要带多厚的外套、如何搭配内层、早晚是否需要多一层**。优先避免带得太厚或太薄，而非提供实时天气服务、精确天气预报或个体舒适度保证。

- **Mobile-first Web**：手机浏览器可直接使用；无需安装、登录、账号或个人资料保存。
- **V1 中文优先**；系统时间、旅行日期和天气窗口均以 `Europe/Berlin` 为准。
- **德国境内城市**：首页精选 10 城，可扩充为 20 城；不声称这是统计意义上的“旅游人数前十/二十名”。自定义查询支持其他可以可靠辨认的德国城市，同名地点须消歧。
- **不做**：即时天气、每小时刷新、雨/雪/风提醒、详细天气图表、时尚搭配、AI/RAG/LangChain、用户数据库、推送、收费和多国支持。V1 只使用气温及其早晚变化判断衣物。

## 2. 用户功能及页面内容

| 功能 | V1 行为 |
| --- | --- |
| 首页查询 | 城市搜索/选择、到达与离开日期、体感（怕冷/一般/怕热；默认一般）、查看建议 |
| 热门目的地 | 预生成的 10 个城市简要建议；显示城市、主要外套结论、必要的气温提醒和数据时间；支持浏览/分页，设计形式留给 UI 阶段 |
| 城市卡片 | 点击后进入该城市查询，预填城市；首页摘要使用统一的 **明日起 7 个完整日**，日期范围明示 |
| 建议结果 | **先给具体外套厚度 + 内搭组合**，再给早晚较冷/温差、明显冷暖变化提醒；不要把内部 L1–L6 当成面向用户的主要内容 |
| 数据说明 | 区分“14 天内预报”与“历史同期备衣参考”；显示数据来源、实际获取时间、建议计算时间以及长短期不确定性 |
| 分享 | 可复制简洁建议；用包含城市 ID、起止日期、体感的链接重开查询，**不永久固化旧天气结论** |
| 反馈 | V1 可预留“偏厚/合适/偏薄”的轻量入口，但不作为上线阻塞条件，也不收集个人身份信息 |

UI 阶段再确定：信息层级、首页与结果页布局、卡片分页/滑动交互、字体、字号、配色、图标、留白及状态页面。这里只要求移动端优先、易读、触摸友好、低流量与基本无障碍支持；**不预设 Next.js 或特定组件库**。

## 3. 输入、规则与输出契约

**输入**：`city_id`（由受控城市搜索解析，不直接信任经纬度输入）、`start` / `end`（ISO 日期）、`preference`（`cold | normal | hot`）。

**日期约束**：`start <= end`、不早于德国当地当天、`end <= 当天+29 天`。整趟行程的结束日不超过当天 +13 天时用 14 天**预报模式**；否则整趟行程统一走 **过去 8 年同期固定 ERA5 历史参考模式**，不得将历史值写成未来逐日预测。保持现有原型“没有完整覆盖即拒绝”的边界。

**气温规则**：复用当前六级衣物模型、13°C 附近的容差、白天 09–18 时以及早 06–08 / 晚 19–22 时窗口；体感只调整穿衣建议，不制造不同天气预报。今天已过去的白天不当作未来。临近跨日按德国当地日期重新验证数据窗口。

**结果应为结构化对象**（而非前端解析 CLI 文本），至少含：
- `city`、`start`、`end`、`preference`、`mode`（`forecast | historical_reference`）；
- `headline`（一条外套决定）、`layers`（主要内搭/可脱层）、`notices[]`（仅气温相关）、`reference_temperature_c`；
- `weather_fetched_at`、`advice_generated_at`、`data_status`（`fresh | stale`）、`source`、`caveat`。

**服务端接口建议**：`GET /api/cities?q=...`、`GET /api/featured`、`GET /api/advice?city_id=&start=&end=&preference=`；另有**非公开调用权限**的每日预取端点。输入错误返回清楚的 4xx，天气或存储失败返回可理解的错误；不提供没有依据的默认衣物建议。

**现有代码必须适配的地方**：
1. 短期默认建议不再无条件请求 2 个历史年份；如保留 CLI 详细历史对比，按需请求。
2. 网页气温模式移除预报及历史解析器对降水、雪和风字段的强制依赖，并移除相关网页提醒；保留或迁移既有 CLI 能力须明确测试边界。
3. 数据获取时间与建议计算时间分开；不得把读取缓存后重新计算的时间标作天气数据更新时间。

## 4. 每日预取与缓存

**核心原则：每天每城市最多按计划更新一次预报；从缓存天气数据计算不同旅行日期/体感，而非每个用户重新查询 Open-Meteo。** 不需要按小时更新。

- **每日预取**：Vercel Cron 暂定 `05:00 UTC` 每天一次（在德国约早 06:00/07:00，Hobby 可能在指定小时内浮动）。为 10 个精选城市获取一次未来 14 个日历日的逐小时 **`temperature_2m`**，使用模型生成“明日起 7 日”摘要，原子性发布一份带日期及 `fetched_at` 的首页快照。日后扩至 20 城只改变城市配置。
- **自定义短期**：同一城市、同一德国日、相同天气变量/模型参数共享一份 14 天预报；缓存命中即按用户日期与体感重算。非精选城市当日首查才访问天气 API。**仅当缓存的 `daily.time` 从德国当地“今天”开始且覆盖选择范围时才能作为新预报使用**。
- **远期历史**：8 个年份的温度样本按 `city_id + ERA5 + 历史日期区间 + 参数版本` 缓存（初始可设约 90 天），重复行程无需再次查询；所有 8 年和早晚窗口完整后才计算。**不预取每城所有历史月份**，有使用数据再决定是否分月复用。
- **共享存储**：V1 拟选 Vercel Marketplace 上的 **Upstash Redis（托管 KV）**，用于天气数据、精选城市快照、TTL、并发锁和限流计数；不需要用户数据库、独立 Redis 服务器或 Vercel 容器本地持久化。密钥仅保存在服务端环境变量。部署前核实当前额度/成本，采用免费档时设置内部预算。
- **版本和有效性**：缓存键含城市稳定 ID、德国日期、数据模型/变量及规则版本；预报新鲜度按**德国日**判断，不盲目认为未过 24 小时就可供下一日计算。旧首页快照最多短暂显示并显著标注旧日期；若超过设定保护期则提示暂不可用，而不是称为最新天气。历史缓存较长，但重新计算的历史年份窗口必须正确。
- **并发与失败保护**：同一缓存键使用共享短租约/锁抑制并发穿透；限制未缓存城市查询次数、上游并发与总 API 预算；对超时/429 做有限退避重试。计划任务幂等、受 `CRON_SECRET` 保护；失败不覆盖上一份完整快照，可手动安全重跑。共享存储失败时不能放开无界上游请求。
- **监测**：只记录匿名聚合的缓存命中、上游请求/估算计费调用、预取成功、4xx/429/超时、查询耗时；不默认保存访客行程或 IP 明文。遵守天气提供商署名和使用许可。

## 5. 部署目标与实现约束

**不使用 VPS**。V1 目标是 **Vercel 托管的一体化 Python Web 服务**（优先 Flask + 服务端 HTML/少量 JS），直接复用原型的 Python 规则；优先尝试官方 `Dockerfile.vercel` 容器 Function，保留普通 Docker 可移植性。**Vercel、托管 KV 和 Docker 的具体组合要在 Preview 上验证才能算部署决策完成**；不要未经测试就宣称支持全部运行场景。

- GitHub 私有仓库、开发分支 PR Preview、主分支正式发布；**生产部署/发布需独立授权**。
- 一个网页服务提供 HTML、API 和受保护的预取入口；无常驻后台进程、无容器本地 SQLite/文件缓存。
- Vercel Cron 只在生产部署自动执行；**Preview 必须有明确的手动测试方式**，且预览与生产使用隔离的缓存命名空间/凭证，避免测试污染生产数据。
- 检查 Docker Function 的冷启动、资源/执行时长、历史 8 年首次获取的延迟；长历史查询使用**有上限的小并发**，不能顺序等待 8 次超时，也不应无界并发。
- V1 只考虑个人、非商业发布；如果上线包含收费、广告或商业推广，须重新确认 Vercel Hobby 及 Open-Meteo 免费 API 资格与许可。
- 公开前验证 Android Chrome、iOS Safari、微信内置浏览器，以及中国内地访问的实际可达性；避免依赖必须跨境加载的第三方字体/图片。

## 6. 验收标准与下一步

- 手机端可以完成 **选城市 → 选日期/体感 → 阅读建议 → 复制/分享链接**；结果清楚区分预报与历史参考。
- 精选 10 城首页来自预取快照，浏览及翻页**不调用 Open-Meteo**；20 城仅需配置扩展。
- 相同城市/德国日的短期查询复用天气数据；用户改变日期/体感不会引发重复预报查询；次日重新获取与日期校验正确。
- 默认网页查询不请求不必要的 2 年短期历史；气温模式不依赖雨、雪、风字段；现有核心衣物规则测试和新增 API/缓存/跨日/故障测试通过。
- 8 年历史冷缓存查询在 Preview 实测符合可用的等待体验或清楚失败，不以部分历史数据生成结论；不超过既定上游预算。
- Cron 安全、可重跑，失败不发布半成品；显示真实 `weather_fetched_at` 和数据状态，天气来源与不确定性可见。
- Preview 可供手机真实使用；记录平台额度、缓存命中率与主要查询耗时，再决定是否正式发布。

**下一阶段：** 在本规格经过 Review/确认后，**先讨论 UI Design**（布局、信息层级、字体、配色与交互），再做完整网页实现。此文档不授权实现、安装集成、上线或合并 PR。
