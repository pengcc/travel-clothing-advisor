## 当前交付方向与实施状态（2026-10-22）

**产品目的：** 帮助赴德国旅行、对当地气候不熟悉的人，根据实际气温预报或过去五年同期气温，决定携带多厚的外套、保暖内搭以及可增减的衣物，避免带得太薄或过厚。产品核心是可执行的备衣建议，不是另一款实时天气预报软件。

**“渐进交付”的定义是逐批扩大实际可用的城市、数据覆盖和更新能力**，每一批都能让用户真实使用；不是只完成基础设施、反复测试同一条链路，也不是要求每天重新下载相同的历史月份。

**发布方向澄清**：未执行公开部署、尚未获得某次 Production 部署授权，**不等于产品决定不公开上线**。Preview 只是阶段验收手段，不能取代让真实用户使用的目标；可根据任一阶段的功能可用性、数据有效性、免费资源额度及许可决定何时对外开放，**不以完成全部历史月份、自动化或 20 城为统一前置条件**。实际部署和访问设置仍须分别核实与授权。

### 当前实际数据架构和边界

```text
本地 Python 下载/校验（Open-Meteo、ERA5）
        ├── 当天十城 14 天预报 → .forecast-local/
        └── 历史月份逐步补齐   → .history-local/
                   ↓ 验证与离线导出／增量合并
        Git: weather-data/（只包含公开、校验合格的数据；保留已有有效历史）
                   ↓ main 合并后触发 Production 自动部署；Preview 仍需手动部署
        Vercel Preview：Python 只读 API + 网页（访问保护按需决定）
```

- 本地 `make dev` 使用 `.forecast-local/` 与 `.history-local/`，且可能补取缺失的当天精选预报；**不会自动把本地缓存同步到 Git 或 Vercel**。网页 Preview 默认读仓库中 `weather-data/` 的当前部署版本，不读取开发者电脑目录，也不会在用户请求时下载天气。
- 现有 `web.prefetch_forecasts`、`web.prefetch_history`、`web.bundle_data` 和 `web.readonly` 分别承担预报准备、历史补齐、离线数据导出及只读服务；`web/README.md#git-weather-bundle` 记录实际命令。**导出仅覆盖当前相关历史窗口，发布者必须把导出结果增量合并到 Git，并逐一保留已积累的有效历史月份**；不可整体清空 `weather-data/`。
- 2026-10-24 的 Git 部署配置调整为只对 `main` 自动部署 Production，其他分支（包括 Preview 分支）不自动部署；Preview 验收仍需明确使用正确的数据提交手动创建。Production 合并必须考虑自动部署的影响。预报按德国当地日期有效，过了午夜需新日期的预报和新部署；历史月文件不会随日切换自动失效。
- `api/index.py` 保留独立的旧 Preview Blob 读取开关 `TRAVEL_PREVIEW_NAMESPACE` 和 P1 SQL/Blob 开关 `TRAVEL_P1_READER`。**默认 Git 只读 Preview 路径不以数据库或 Blob 为前置条件**；这些路径虽已有代码，但相关自动运营与真实费用门槛不能写成已启用。现有 Production 路径仍有保护/未启用边界；Preview 验收不等于已执行公开上线，也不意味着永久不公开。
- 免费资源是硬约束：不购买 VPS、不升级付费套餐；手工 Preview 和未来自动方案都须遵守已核实的账户额度、供应商许可及按实际需求决定的访问设置。无需为第一批十城人工发布先配置 SQL、Blob 或 Cron；未来若要支持任意城市查询时动态共享/持久化，可另行明确需求与架构，不追溯改写已交付阶段。

## 1. 产品目标与边界

帮助不熟悉德国天气的旅行者回答：**旅行时需要带多厚的外套、如何搭配内层、早晚是否需要多一层**。优先避免带得太厚或太薄，而非提供实时天气服务、精确天气预报或个体舒适度保证。

- **Mobile-first Web**：手机浏览器可直接使用；无需安装、登录、账号或个人资料保存。
- **V1 中文优先**；系统时间、旅行日期和天气窗口均以 `Europe/Berlin` 为准。
- **德国境内城市**：第一批首页精选固定 10 城；运行稳定后再考虑扩充到 20 城；100 城仅是未批准的远期候选。不声称这十/二十城是统计意义上的旅游热门排名。自定义查询在支持真实城市解析和数据获取的运行环境中可选其他德国城市，同名地点须消歧；当前 Git 只读 Preview 的可用资料不等同于全德国覆盖。
- **不做**：即时天气、每小时刷新、雨/雪/风提醒、详细天气图表、时尚搭配、AI/RAG/LangChain、用户数据库、推送、收费和多国支持。V1 只使用气温及其早晚变化判断衣物。

## 3. 输入、规则与输出契约

**输入**：`city_id`（由受控城市搜索解析，不直接信任经纬度输入）、`start` / `end`（ISO 日期）、`preference`（`cold | normal | hot`）。

**日期约束与数据优先级**：`start <= end`、不早于德国当地当天、`end <= 当天+29 天`。整趟行程的结束日不超过当天 +13 天时**优先使用有效的 14 天预报**；在当前独立城市的 Git 只读 Preview 中，如预报缺失、过期或无效，仅当整趟所需的**最近 5 个对应年度行程窗口的 ERA5 历史资料完整**时，回退为 `historical_reference`，否则返回不可用，不补造结果。行程结束日超过当天 +13 天、但不超过 +29 天时，**整趟统一使用**上述完整五年历史参考，不与部分预报拼接。返回值须明确区分 `forecast` 与 `historical_reference` 模式及来源；历史参考不能写成未来逐日预测。Git 只读网页请求不触发新的预报或历史下载。保持“没有完整覆盖即拒绝”的边界。

**气温规则**：复用当前六级衣物模型、13°C 附近的容差、白天 09–18 时以及早 06–08 / 晚 19–22 时窗口；体感只调整穿衣建议，不制造不同天气预报。今天已过去的白天不当作未来。临近跨日按德国当地日期重新验证数据窗口。

**冷暖变化／备衣风险提醒（独立于主档位）**：

- **目标**：防止旅行者漏带较冷情况下必要的外套或保暖层，也防止偏暖时无法脱减衣物。建议是打包时的提醒和参考，最终如何搭配由用户决定。
- **预报模式按实际日期触发**：只要任一有完整有效气温预报的日期与其他日期相比，足以改变该带的外套或可增减层次，就应生成明显提醒。**即使三天只有一天异常，也应提醒**。L2→L4→L2（如 24°C、14°C、24°C）与 L4→L2→L4 均为必须覆盖的正反场景。跨两档是明显例子，不以固定天数、两档出现比例或中位数代表性作为提醒前提；边界附近很小的气温波动且不影响备衣时不应提醒。
- **历史模式只提示备衣风险**：比较五个完整对应年度行程窗口中的有依据冷暖范围及其衣物需求；如历史样本显示某些较冷／较暖条件会改变该带的外套或可脱层次，则生成提醒，但**不能把某个历史日期映射为这次旅行将发生冷暖变化的未来日期**。历史中不存在有意义的备衣差异时保持 `null`，不为了填满卡片而制造警告。
- **输出保持轻量**：主结论先明确应考虑的外套厚度；独立的醒目提醒紧随主句，预报模式可标示有依据的日期，历史模式只表述样本中的偏冷／偏暖备衣风险。不是逐日穿搭表，不硬性指定组合；早晚温差另按实际需要处理。
- **主档位与提醒分开**：当单一等级具有代表性时，照常返回该等级；*仍然可以同时返回变化提醒*。只有冷热分布严重分化、没有可解释的代表性等级时，保暖等级才可设为 `null`；例如 7 天 L2 + 7 天 L4 的中位数落在无人出现的 L3，不能称 L3 是多数天的穿法。**`null` 不等于只需泛泛提醒叠穿**：如果有效预报或五年历史样本支持需要 L6 冬季保暖的可信偏冷情况，主句和内搭必须明确说明冬季保暖外套、保暖内搭／抓绒，以及偏暖时可减薄的选择。不得用 `warmth_indicator_level=null` 作为显示变化提醒的必要条件；无代表性时也不能伪造单一代表温度。
- **不确定性**：第 8–14 天的温差仍可提醒，但要注明预报较远、出发前复查；历史参考仅据最近五个对应年度行程窗口讨论可能的备衣范围，不能断言未来某天会冷/热。检测沿用或扩展后端 Python 逐日模型，前端不创建另一套温度规则。

**结果应为结构化对象**（而非前端解析 CLI 文本），至少含：
- `city`、`start`、`end`、`preference`、`mode`（`forecast | historical_reference`）；
- `headline`（一条外套决定）、`layers`（主要内搭/可脱层）、`notices[]`（其他气温相关提示）、`reference_temperature_c`；
- `packing_variation_notice`（**必有字段，简短字符串或 `null`**）：依据有效数据且确实会影响备衣才生成；即使主等级存在也可以非空。**预报模式**可给出预报支持的偏冷／偏暖日期或范围及应多备／可脱的衣物；**历史参考模式**只能写明过去五年同期样本中观察到的备衣风险（可说明历史年份，**不得断言这次旅行中的任何具体日期会冷／热**）。例如预报「10 月 20 日偏冷：带适中外套」；历史「过去五年同期曾出现需要冬季保暖外套的偏冷情况，可另备保暖内搭；暖时换轻薄内搭」，不得写成「11 月 23 日将偏冷」。无有意义变化则为 `null`。该字段在结果页**紧跟外套结论、优先于内搭及早晚提醒**，不在 `notices[]` 中重复堆叠；
- **精选城市预取快照另提供** `packing_variation_summary: string | null`（必有字段）：与相同德国日期、相同预报数据版本、相同有效预测时段下的完整结果 `packing_variation_notice` **来自同一后端逐日判断**，有变化则两者均非空，无变化则两者均为 `null`。摘要是**面向卡片独立写成的一句短而完整的中文备衣提醒**（说明偏冷/偏暖和可带/可脱的层次），无需复制全部日期和长说明；不得由前端截断完整通知、重新分析气温或硬拼接文案。移动端若字数超出一行可换行，不以省略号隐藏关键意思；
- `warmth_indicator_level`（**必有字段，值为 1–6 或 `null`**）：服务端从现有六档衣物模型与逐日分布生成可展示的主档位，精选城市摘要也带同字段；当没有代表性的主档位才置 `null`，UI 不显示误导性单档信号格而改为文字提示；**这与 `packing_variation_notice` 是否存在相互独立**，例如 L2→L4→L2 可有明确 L2 主档且同时出现提醒；客户端不得根据气温重新计算等级；
- `weather_fetched_at`、`advice_generated_at`、`data_status`（`fresh | stale`）、`source`、`caveat`。

**服务端接口建议**：`GET /api/cities?q=...`、`GET /api/featured`、`GET /api/advice?city_id=&start=&end=&preference=`；另有**非公开调用权限**的每日预取端点。**分享与路由契约**（示例 URL 参数，不强制框架）：行程链接 `?view=trip&city_id=...&start=...&end=...&preference=...`；城市参考链接 `?view=city&city_id=...`。应用层识别 `view=city` 时，仅以德国当地今天到 +13 天、`normal` 重新生成结果，不能读取或改写已输入的个人行程；无需另外增加独立天气 API。城市参考跨日打开也必须重新验证覆盖范围，不照搬昨天的结果。输入错误返回清楚的 4xx，天气或存储失败返回可理解的错误；不提供没有依据的默认衣物建议。

**现有代码必须适配的地方**：
1. 短期默认建议不再无条件请求 2 个历史年份；如保留 CLI 详细历史对比，按需请求。
2. 网页气温模式移除预报及历史解析器对降水、雪和风字段的强制依赖，并移除相关网页提醒；保留或迁移既有 CLI 能力须明确测试边界。
3. 数据获取时间与建议计算时间分开；不得把读取缓存后重新计算的时间标作天气数据更新时间。

## 4. 14 天预报缓存与五年 ERA5 历史资料库

**数据分开存，衣物规则共享。** 短期预报按德国日更新，历史资料提前分批获取、验证后长期保存；用户更换城市、日期或体感，只根据可用气温重新计算建议，不为每人单独存一份结果。当前 Preview 的实际已发布数据源是 Git `weather-data/`；下面 4.1–4.3 的多实例自动缓存、额度协调等部分为长期目标，不应理解为当前 Git Preview 已启用。Phase 2B 原始实现范围见 [Issue #21](https://github.com/pengcc/travel-clothing-advisor/issues/21)。

### 4.1 14 天预报（Phase 2C 的共享缓存目标）

- **精选城市预取目标**：为首页第一批 10 座城市，每个德国日准备当天至 +13 天的完整逐小时 `temperature_2m`，并由同一真实数据生成卡片和详情。**当前先人工准备、校验、更新 Git 并部署 Preview 验证；第三阶段再自动化每日更新**。扩充至 20 城属于独立后续交付；不做逐小时更新。其他城市按需获取属于后续动态支持范围，不要求第一阶段完成。
- **缓存键和共享**：`城市 GeoNames ID + 坐标/天气参数版本 + 德国当地日期`。同城市当天所有行程日期、体感和精选城市共用这份预报；每次按选定时段重新运行衣物规则。**当前本地用磁盘缓存，Preview 用 Git 版本化只读数据文件**；若以后改为动态共享持久存储，再单独评估多实例和访问权限。PR #20 的 Python 进程内字典只是早期临时优化。
- **有效性**：检查气温单位、原始小时顺序、日期及 06–22 所需时段的完整覆盖，使用 Unix 时间点和柏林时区正确处理夏令时。跨德国午夜必须重新检查今天的完整 14 天范围，不将昨日预报冒充今日结果。分开记录实际 `weather_fetched_at` 与 `advice_generated_at`，不宣称是提供方模型更新时间。无有效新快照时不能冒充预报；当前 Git 只读 Preview 仅在对应五年历史完整时可退回历史参考，否则明确不可用；失败不发布半成品。
- **执行时点**：先用本地受限下载和人工 Git/Preview 发布，提供可用的十城预报；之后才为**同一条经过验证的发布链路**添加定时触发、失败重试与配额控制。已有另一条默认禁用的 P1 worker 不能冒充 Git 路径自动运行。

### 4.2 最近五年历史气温（Phase 2B）

- **五年窗口**：旅行有日期超过当日 +13 天、但整趟在 +29 天内时，**整趟统一使用最近五个对应既往年度的行程窗口**，不混入一部分未来预报。必须五年完整；不能静默跳过缺失年份、退化成四年、或换成更老的替代年份。
- **确定性历史日期映射（每个年度完整连续）**：用用户行程的**到达日所在年份**作为锚点，取 `anchor_year-1` 到 `anchor_year-5` 五个年份。原行程长度以**包含首尾的德国本地日历天数** `N=(end-start).days+1` 计算。对每个历史年份，把原**到达日的月／日**替换到该年份，得到历史起始日期；仅在原到达日为 **2 月 29 日**而目标年无闰日时，改用目标年的 **2 月 28 日**作为起点。历史结束日期一律按 `历史开始日 + (N-1) 个日历日` 推出，**绝不独立替换结束日年份，也不逐日把 2 月 29 日折叠到 2 月 28 日**。五段各自必须连续、无重复日期、与原行程拥有相同 N 天；夏令时日期仍按当地日历天数计算，不能假设每天恰好 24 个小时。
- **日期映射验收例子**：原行程 `2026-12-29～2027-01-03`（6 天）映射为 `2025-12-29～2026-01-03`、`2024-12-29～2025-01-03`，并类推到五年；原行程 `2028-02-28～2028-03-01`（闰年 3 天）映射到非闰年的 `2027-02-28～2027-03-02`，到闰年的 `2024-02-28～2024-03-01`；原行程 `2028-02-29～2028-03-02`（3 天）映射到 `2027-02-28～2027-03-02`（非闰年）和 `2024-02-29～2024-03-02`（闰年）。闰年对照的末日可能与旅行原始月日相差一天，这是为保留**同季节的连续 N 天**而接受的近似，不能声称逐日历日完全相同。预下载任务必须以**计算出的五段实际范围**检查所需年月（包括跨月／跨年），并测试上述三个例子及缺块处理。
- **数据源**：Open-Meteo Historical Weather API，固定 `models=era5`，**只取** `hourly=temperature_2m`、摄氏度、`timezone=Europe/Berlin`、`timeformat=unixtime`。验证逐小时 UTC 时间戳、完整日期/时段、数值、单位和 DST；用 09–18 白天及 06–08、19–22 早晚气温生成备衣参考。历史资料只能表达可能的冷暖范围，不可伪造此次旅行的具体哪天更冷/更暖。
- **存储单位**：`城市 GeoNames ID + 坐标版本 + ERA5/变量/时区/数据格式版本 + 年月`。每个月份保存完整、已验证的历史逐小时气温和来源、获取时间、校验摘要。例如 `history/era5/temp-v1/<city-id>/<coordinate-version>/<yyyy-mm>.json.gz`。不同人的重叠行程直接提取已存月份中的对应日期；调整体感不重新请求气象 API。
- **预下载优先级**：独立于用户查询、分批和幂等运行：先准备 10 个精选城市接下来 30 天可能涉及的五年历史月份，然后逐步补齐其五年全年。其他德国城市可以预算内按需补缺。每次只读取缺月清单并补缺；下载中断后保留已成功月份；一个块全部验证成功才原子发布，不保存半成品。无需先完成所有城市全年下载才能支持资料已齐备的行程。
- **长期保存**：历史月块是可长期复用的版本化资料，不是按用户行程存 90 天的缓存；无需每天刷新，也不默认要求 Redis 或用户数据库。当前阶段将通过校验的历史月份逐批、**增量**保存到 Git `weather-data/`，绝不在下一次导出/同步时丢弃以前有效月份。可以在资料参数发生变化时换版本，并在新一年滚动补充新进入参考窗口的历史年份；如以后转向多实例动态写入，则另行选定共享存储，不能使用 Vercel 的临时容器文件当长期数据。
- **真实性与容错**：下载、读取、时间窗口匹配、对象版本或数据完整性失败时，不以不完整样本生成「五年」结论，也不返回貌似真实的默认衣物建议。显示「过去五年同期气温参考，非这趟行程的预报」，分别记录历史资料实际获取时间和建议计算时间。历史较冷样本只作为备衣风险提示，不把对应历史日期当成今年逐日预测。若最新的必要历史月份因 ERA5 数据发布延迟尚未完整，返回明确不可用，不拿其他年份替补。
- **Python 原型边界**：现有 `experiments/clothing-rules/trip_advisor.py` 仍采用八年历史查询和额外降水/雪数据，是尚未改动的独立 CLI 实验；不是 Phase 2B 网页契约，不要误称其已经是五年实现，且网页不得复制其逐人逐年请求逻辑。

### 4.3 请求预算和执行方式

- **可重复执行、受控的补取**：Phase 2B 提供可注入 provider/clock/store 的 Python 历史获取接口和受控的手动预下载入口。默认只请求缺失月块，限制执行批次、上游并发（初期至多 2）、请求总超时、429/5xx 失败冷却；绝不在普通用户请求里无限等待。
- **配额**：记录 HTTP 请求次数及按时间范围、变量等保守估算的 Open-Meteo 加权 API calls，不假设一个长时间 HTTP 请求就只消耗一个额度单位；设置可配置的每批、每日和每月内部预算，并留足预报和地理编码余量。对象存储不天然提供跨实例分布式锁或原子全局额度计数；未建立可靠协调时，预下载采用受保护的单执行入口，其他补缺受严格限制，不能声称全局限流已实现。
- **故障与观测**：对存储缺失/损坏、部分年份失败、预算耗尽、重复请求、德国日期变化、模型版本变化和 DST 提供确定性离线测试。只记录资料块数量、成功/失败、缓存命中和 API 用量，不保存个人行程或明文 IP。
- **阶段边界**：Phase 2B 完成五年历史接口、预下载/读取与 15–30 天行程建议的本地实现；Phase 2C 才实现预测共享缓存、精选城市真实快照与定时更新；Phase 2D 才选择并配置对象存储、下载实际生产资料、部署 Preview 和验证平台成本。文档计划本身不授权外部下载、开通服务或发布。

## 5. 部署目标与实现约束

**坚持完全免费资源**：不购买 VPS、不升级付费套餐。正式对外部署属于可随渐进交付进度决定的下一步，不是已经排除的产品方向；实际部署仍须获得单独授权，并在免费额度、许可与数据可用性满足要求后进行。V1 移动端优先、中文优先、Python 气温及衣物规则共享；不强制 Docker、Next.js 或引入额外 AI/ML 技术。

### 5.1 当前有效的人工 Preview 路径（第一阶段）

- 本地 `web.server`、`web.prefetch_forecasts`、`web.prefetch_history` 和 `web.bundle_data` 已实现。天气数据来自 Open-Meteo 预报及 ERA5 历史 API，经过城市身份、气温时段/时区和文件完整性校验；**普通网页读请求不下载天气**。

### 5.2 后续自动化与上线边界

## 6. 验收标准与下一步

- 手机端分别完成 **按行程查询：选城市 → 选日期/体感 → 查看该行程建议**，以及 **精选城市：点击城市 → 直接查看今起14天参考**；各自返回并保留状态、复制/分享对应链接；结果区分预报与历史参考。
- 精选 10 城首页优先读取当日有效的预取预报；当前 Git 只读 Preview 预报缺失/过期时，仅在该城市对应五年历史完整时显示明确标注来源的历史参考，否则显示缺失状态；浏览及翻页**不调用 Open-Meteo**；点击直接查看该城市今天起 14 天的独立结果，**不要求输入日期，也不影响行程查询**；首页快照包含 `warmth_indicator_level` 与 `packing_variation_summary`（均可为 `null`），结果页包含 `warmth_indicator_level` 与 `packing_variation_notice`（均可为 `null`）。针对**相同日期/天气数据版本**的有无变化判断一致；卡片摘要用完整的短句而非裁切结果页文本，结果页提醒紧跟外套结论，不能以单档等级遮盖某一天明显偏冷/偏暖。
- **20 城扩展（未来独立阶段，非当前十城验收）**：需单独调整并验证代码的十城限制、城市清单与 Manifest、天气获取及存储配额、首页 UI/分页和 Preview 部署；不得只修改配置就宣称 20 城已经可用。
- 相同城市/德国日的短期查询复用天气数据；用户改变日期/体感不重复取预报；只含 hourly 气温的响应能完整校验 14 天，**本地跨日/旧缓存不冒充新预报**。
- 默认网页查询不请求不必要的 2 年短期历史；气温模式不依赖雨、雪、风字段；现有核心衣物规则测试和新增 API/缓存/跨日/故障测试通过。**增加跨日冷热变化验收**：① 3 天 L2→L4→L2，偏冷仅 1 天也有醒目的备衣提醒，但主档位仍可为 L2；② 3 天 L4→L2→L4，偏暖仅 1 天也提醒可穿脱/减薄，不把所有天描述为同样冷；③ 14 天 7 天 L2 + 7 天 L4 不把中位数 L3 称为「多数日子」，主档不具代表性时允许为 `null`，仍要显示变化提醒；④ 稳定同档或仅边界附近轻微波动时不制造变化提醒；⑤ 第 8–14 天用不确定性措辞；⑥ 验证城市/行程分享链接参数隔离及德国当地跨日重新计算。提醒不能依赖 `warmth_indicator_level=null` 才出现。
- 五年历史增量预下载可断点继续、只补缺月；完整资料命中时历史 API 请求为零，缺月时预算内补取或明确失败，不以部分年份生成结论；Preview 测量响应时延和实际 API 用量。
- 历史映射验收：跨 `2026-12-29～2027-01-03`、含闰日 `2028-02-28～2028-03-01` 和以闰日出发 `2028-02-29～2028-03-02`，均保持五段**连续、无重复、与原行程相同本地日历天数**；不足五段完整小时资料时不返回历史建议。
- 提醒语义验收：短期预报 `L2→L4→L2` 可点名有依据的偏冷日期；五年历史样本若含 L2 与可信 L6 冬季偏冷风险，可提醒「过去五年同期曾出现需要冬季保暖外套、保暖内搭的情况」，不得点名未来某天会偏冷，且无代表性主档时 `warmth_indicator_level`／`reference_temperature_c` 均可为 `null`，但主外套结论仍须包含明确冬季外套需求和暖天可减薄的内搭。
- 第一阶段先验收**人工**发布的真实十城数据：Git 变更内容正确、Preview 部署确实使用该版本、卡片和详情来自同一真实源并显示 `weather_fetched_at`；跨德国午夜不冒充当天预报。第三阶段自动化应另验收定时执行、失败恢复和无半成品发布，未运行之前不得标注已实现。
- Preview 可供手机真实使用；记录平台额度、缓存命中率与主要查询耗时，再决定是否正式发布。
