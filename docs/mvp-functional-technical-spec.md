# Travel Clothing Advisor — MVP Functional & Technical Specification

> **版本：** V1 目标规格（待 PR 审阅/合并） · 2026-10-15  
> **范围：** 德国旅行穿衣建议网站的功能、输入输出、天气数据、缓存和部署；**不是 UI 视觉设计稿，也不是已实现功能**。  
> **依据：** 用户在 2026-10-15 的产品取舍；现有 `main` 上 PR #14 的 Python 原型。

## 1. 产品目标与边界

帮助不熟悉德国天气的旅行者回答：**旅行时需要带多厚的外套、如何搭配内层、早晚是否需要多一层**。优先避免带得太厚或太薄，而非提供实时天气服务、精确天气预报或个体舒适度保证。

- **Mobile-first Web**：手机浏览器可直接使用；无需安装、登录、账号或个人资料保存。
- **V1 中文优先**；系统时间、旅行日期和天气窗口均以 `Europe/Berlin` 为准。
- **德国境内城市**：首页精选 10 城，可扩充为 20 城；不声称这是统计意义上的“旅游人数前十/二十名”。自定义查询支持其他可以可靠辨认的德国城市，同名地点须消歧。
- **不做**：即时天气、每小时刷新、雨/雪/风提醒、详细天气图表、时尚搭配、AI/RAG/LangChain、用户数据库、推送、收费和多国支持。V1 只使用气温及其早晚变化判断衣物。

## 2. 用户功能及页面内容

| 功能 | V1 行为 |
| --- | --- |
| 按行程查询 | 城市搜索/选择、到达与离开日期、体感（怕冷/一般/怕热；默认一般）、查看**该趟行程**的建议；不使用精选城市栏目的日期或状态 |
| 精选城市（独立栏目） | 预生成 10 个德国城市的**今起 14 个日历日（含今天）**穿衣参考：城市、外套结论、主要气温提醒、实际数据时间；可浏览/分页。**不读取或改变上方行程查询的城市、日期、体感。** |
| 精选城市卡片 | **点击直接打开该城市的独立 14 天参考结果**，无需填日期；固定 `start=德国当地今天`、`end=今天+13 天`、`preference=normal`，展示覆盖日期。返回首页保留独立行程表单的输入。 |
| 两种独立结果 | 「行程穿衣建议」与「城市穿衣参考」可复用展示组件，但**入口、日期来源、返回动作和分享链接各自独立**。先给具体外套厚度 + 内搭组合，再给早晚温差和关键提醒；不显示内部 L1–L6。 |
| 数据说明 | 区分“14 天内预报”与“历史同期备衣参考”；显示数据来源、实际获取时间、建议计算时间以及长短期不确定性 |
| 分享 | 可复制简洁建议；用包含城市 ID、起止日期、体感的链接重开查询，**不永久固化旧天气结论** |
| 反馈 | V1 可预留“偏厚/合适/偏薄”的轻量入口，但不作为上线阻塞条件，也不收集个人身份信息 |

UI 阶段再确定：信息层级、首页与结果页布局、卡片分页/滑动交互、字体、字号、配色、图标、留白及状态页面。这里只要求移动端优先、易读、触摸友好、低流量与基本无障碍支持；**不预设 Next.js 或特定组件库**。

## 3. 输入、规则与输出契约

**输入**：`city_id`（由受控城市搜索解析，不直接信任经纬度输入）、`start` / `end`（ISO 日期）、`preference`（`cold | normal | hot`）。

**日期约束**：`start <= end`、不早于德国当地当天、`end <= 当天+29 天`。整趟行程的结束日不超过当天 +13 天时用 14 天**预报模式**；否则整趟行程统一走 **过去 8 年同期固定 ERA5 历史参考模式**，不得将历史值写成未来逐日预测。保持现有原型“没有完整覆盖即拒绝”的边界。

**气温规则**：复用当前六级衣物模型、13°C 附近的容差、白天 09–18 时以及早 06–08 / 晚 19–22 时窗口；体感只调整穿衣建议，不制造不同天气预报。今天已过去的白天不当作未来。临近跨日按德国当地日期重新验证数据窗口。**多日行程必须区分主流穿法、较冷日期要覆盖的额外衣物和较暖日期可减的层次**；例如白天气温跨 L2→L4 时不能仅展示中位数 L3 的单档结论，也不应因为少数冷天要求整段行程穿同样厚的外套。跨日温差与早晚温差分别说明；后期预报及历史参考明确不确定性。具体跨度判断沿用或扩展 Python 模型，**不由前端重新定义阈值**。

**结果应为结构化对象**（而非前端解析 CLI 文本），至少含：
- `city`、`start`、`end`、`preference`、`mode`（`forecast | historical_reference`）；
- `headline`（一条外套决定）、`layers`（主要内搭/可脱层）、`notices[]`（仅气温相关）、`reference_temperature_c`；
- `weather_fetched_at`、`advice_generated_at`、`data_status`（`fresh | stale`）、`source`、`caveat`。

**服务端接口建议**：`GET /api/cities?q=...`、`GET /api/featured`、`GET /api/advice?city_id=&start=&end=&preference=`；另有**非公开调用权限**的每日预取端点。输入错误返回清楚的 4xx，天气或存储失败返回可理解的错误；不提供没有依据的默认衣物建议。

**现有代码必须适配的地方**：
1. 短期默认建议不再无条件请求 2 个历史年份；如保留 CLI 详细历史对比，按需请求。
2. 网页气温模式移除预报及历史解析器对降水、雪和风字段的强制依赖，并移除相关网页提醒；保留或迁移既有 CLI 能力须明确测试边界。
3. 数据获取时间与建议计算时间分开；不得把读取缓存后重新计算的时间标作天气数据更新时间。

## 4. 每日预取与缓存

**核心原则：通常每天更新一次每城市的预报；同一天的不同旅行日期/体感共享天气数据。** 不需要按小时刷新。首次部署、德国当地跨日或计划任务失败时，允许有预算限制的按需补取，不能因此展示日期不符的数据。

- **每日预取**：每日定时任务（Vercel Cron 候选）暂定 `05:00 UTC` 执行一次；为 10 个精选城市获取**德国当地今天至今天+13天**的逐小时 **`temperature_2m`**，生成同一完整 14 天窗口的城市摘要，完整生成后发布带日期范围和 `weather_fetched_at` 的首页快照。可扩至 20 城，不引入第二种计算规则。
- **自定义短期及完整性校验**：同一城市、同一德国日、相同天气变量/模型参数共享一份 14 天预报；不同日期/体感只重新计算。非精选城市按需获取。**若只请求 hourly `temperature_2m`，就以响应的 `timezone`、`hourly.time` 与温度值验证从德国当地今天起连续 14 个日历日及计算所需时段的完整覆盖，不得依赖未请求的 `daily.time`**。现有解析器需同步去掉对降水、雪、风的 daily 强制校验。
- **远期历史**：8 个年份的温度样本按 `city_id + ERA5 + 历史日期区间 + 参数版本` 缓存（初始可设约 90 天），重复行程无需再次查询；所有 8 年和早晚窗口完整后才计算。**不预取每城所有历史月份**，有使用数据再决定是否分月复用。
- **共享存储**：使用**一个**托管共享缓存保存当天预报、精选城市快照及按需历史数据；Upstash Redis/KV 是候选而非预先锁定的依赖。按实际访问方式和免费额度在 Preview 中决定；不使用函数内存或临时文件作为跨实例持久缓存，不引入用户数据库或独立缓存服务器。密钥仅放服务端。
- **版本和有效性**：缓存键含城市 ID、德国日期、天气参数版本；穿衣结果按当前规则重算。预报只在其覆盖的德国当地日期内有效，**不能跨午夜将昨日 14 天窗口冒充今日窗口**。旧首页快照如短暂保留，必须同时保留其原日期范围与更新时间，不得重新标为今天；不适用时显示暂不可用。历史缓存可以较长，但须匹配年份和旅行日期范围。
- **首次部署、跨日与失败**：Preview / 首次生产发布通过受保护的手动预取初始化首页；德国午夜后、Cron 尚未执行或预取失败时，单个城市查询可**受限地按需补取当天预报**，仍以每天一次计划更新为常态。上游请求须有超时、简单限流/预算和失败提示；429 不进行无限重试。预取任务幂等且受鉴权保护，失败不发布半成品，允许手动重跑。仅在实际并发测试出现缓存穿透时才考虑分布式锁。
- **最低限度观察**：记录预取是否成功、上游调用量和查询失败/耗时；必要时再增加缓存命中率等指标。不默认保存访客行程或 IP 明文；保留天气来源署名并遵守使用许可。

## 5. 部署目标与实现约束

**不使用 VPS**。V1 优先验证 **Vercel 原生 Python/Flask Web 服务**（服务端 HTML + 少量 JS），复用现有 Python 规则；无特殊系统依赖时**不强制 Docker**，需要时再验证 `Dockerfile.vercel`。共享缓存服务也只在 Preview 中选择最简单的可用方案；部署方案以实际验证为准。

- GitHub 私有仓库、开发分支 PR Preview、主分支正式发布；**生产部署/发布需独立授权**。
- 一个网页服务提供 HTML、API 和受保护的预取入口；无常驻后台进程、无容器本地 SQLite/文件缓存。
- Vercel Cron 在生产环境运行；**Preview 提供受保护的手动预取/初始化途径**。Preview 与生产至少隔离缓存命名空间，避免测试污染生产数据。首次生产发布也必须在公开前生成首页快照。
- 在 Preview 实测 Python 服务冷启动、执行时限和 8 年历史查询的首次响应时间；设置**整个请求的总超时上限**，超限明确失败。只有实际速度不足时才考虑少量并发或进一步缓存优化。
- V1 只考虑个人、非商业发布；如果上线包含收费、广告或商业推广，须重新确认 Vercel Hobby 及 Open-Meteo 免费 API 资格与许可。
- 公开前验证 Android Chrome、iOS Safari、微信内置浏览器，以及中国内地访问的实际可达性；避免依赖必须跨境加载的第三方字体/图片。

## 6. 验收标准与下一步

- 手机端分别完成 **按行程查询：选城市 → 选日期/体感 → 查看该行程建议**，以及 **精选城市：点击城市 → 直接查看今起14天参考**；各自返回并保留状态、复制/分享对应链接；结果区分预报与历史参考。
- 精选 10 城首页来自预取快照，浏览及翻页**不调用 Open-Meteo**；点击直接查看该城市今天起 14 天的独立结果，**不要求输入日期，也不影响行程查询**；20 城仅需配置扩展。
- 相同城市/德国日的短期查询复用天气数据；用户改变日期/体感不重复取预报；只含 hourly 气温的响应能完整校验 14 天，**本地跨日/旧缓存不冒充新预报**。
- 默认网页查询不请求不必要的 2 年短期历史；气温模式不依赖雨、雪、风字段；现有核心衣物规则测试和新增 API/缓存/跨日/故障测试通过。
- 8 年历史冷缓存查询在 Preview 实测符合可用的等待体验或清楚失败，不以部分历史数据生成结论；不超过既定上游预算。
- 首次部署可初始化首页；Cron 安全、可重跑，失败不发布半成品；清楚显示旧首页快照或不可用状态。显示真实 `weather_fetched_at` 和数据状态，天气来源与不确定性可见。
- Preview 可供手机真实使用；记录平台额度、缓存命中率与主要查询耗时，再决定是否正式发布。

**下一阶段：** 在本规格经过 Review/确认后，**先讨论 UI Design**（布局、信息层级、字体、配色与交互），再做完整网页实现。此文档不授权实现、安装集成、上线或合并 PR。
